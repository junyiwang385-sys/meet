# RK1828 会议助手 · 技术方案与选型

> 整理日期：2026-08-09；状态更新：2026-08-10  
> 依据：2026-08-05 ~ 08-10 板端验证结果 + 后续架构讨论  
> 定位：会后离线、纯板端（RK1828）的本地会议纪要助手

> **状态说明**：本文同时包含已验证能力和后续设计。Qwen3-ASR Batch worker 已于 2026-08-10 完成全量验证；长会议 map-reduce 纪要、术语纠错和完整离线编排器仍待实现。

---

## 一、两个已定架构决策（一切设计的前提）

| 决策 | 选择 | 影响 |
|---|---|---|
| **实时性** | **会后离线批处理** | 不做流式；重 NPU 负载错峰到会后空闲时段 |
| **部署端** | **纯板端 RK1828**（预留算力外移接口） | 全链路端侧离线；跨架构多端打包不在本项目范围 |

**核心洞察：开发板 = 房东，投影仪 = 租客。**
现在在开发板上会议助手独占芯片；实际产品是投影仪内置，SoC 要和投影主业务（画面处理/UI/投屏/远场语音）共享 NPU、内存、散热。因此：
- 会议助手是投影仪上的**客人**，不能假设独占 NPU；受固件**内存预算**约束；会议是**安静场景**，NPU 拉满会有**风扇噪音**。
- **"会后离线"恰好是端侧可行的关键**：会中只做轻量录音（几乎不吃 NPU），会后投影空闲时才跑 ASR/LLM 重活——天然避开资源争抢和风扇噪音。这是 MQ 削峰 / 错峰的思想。

## 二、总体架构（采集与处理分离）

```
┌─ 会中（低负载，不碰 NPU 大模型）────────────┐
│  麦克风阵列 → 音频采集 → 落盘（分段 wav）      │
│  可选：轻量 VAD 标记（纯 CPU）                 │
└──────────────────┬─────────────────────────┘
                   │ 会议结束 / 用户触发
                   ▼
┌─ 会后（投影空闲，NPU 可用）─────────────────┐
│  离线编排器（单进程，有状态，可断点续跑）       │
│   ① CPU 阶段：VAD → CAM++ diar → 切片 plan    │
│   ② NPU 阶段A：Qwen3-ASR（常驻加载一次跑完）   │→ 卸载释放 NPU
│   ③ NPU 阶段B：Qwen3-4B 纪要生成               │
│   铁律：②③绝不同时占 NPU（离线批处理=程序顺序，不需锁）│
└──────────────────┬─────────────────────────┘
                   ▼
          纪要 JSON → 推送（UI / App / 邮件）
```

## 三、完整处理链路（Pipeline）

```
会议音频
 → VAD（能量+百分位阈值，CPU）
 → CAM++ ONNX 说话人 embedding（CPU，3s 窗）
 → cosine 聚类（阈值 0.68）+ unknown 后处理 → speaker 时间轴
 → ASR 切片合并（bridge4：同 speaker 合并 + 短 unknown bridge，max 30s）
 → Qwen3-ASR 分段转写（NPU）
 → speaker + text 合并 → transcript
 → 专名纠错（术语库 RAG + 拼音匹配 + LLM 判定）  ← P1
 → Qwen3-4B map-reduce 总结（NPU）              ← P0
 → 会议纪要 JSON
```

## 七、P0：纪要生成（map-reduce 分层总结）

**问题**：transcript 约 9000~14000 字，可能超过板端 Qwen3-4B 的有效输入预算；长 prompt 曾导致空输出或坏 JSON。是否超限不能只按字数判断，应以实际 runtime `-c`、同款 tokenizer、固定 prompt/schema 和输出预留共同计算。

**硬约束**：当前稳定 server 以 `-c 4096` 运行；先固定纪要 schema 和 Golden Set，再实测不同单段 token 预算，不能预先把“4 段”写死为结论。

**单次输入预算（以 4K 上下文为例）**：
```
4096 - 指令/schema ~500 - 输出留白 ~800 = 输入 ~2800 token ≈ 1500~1800 中文字
```

**切分器（不依赖主题，按长度预算 + 吸附安全边界）**：
```
优先级：① speaker 切换 → ② 长静音/VAD gap → ③ 句末标点 → ④ 硬切 + overlap(10~15%)
```
- 有主题结构：自然落在 speaker 切换点。
- 全程单一主题/独白：降级为固定窗口滑动切分（带 overlap，防边界截断）。

**两级 map-reduce**：
```
MAP：  每段 → 局部要点 JSON {topic, speakers, time_range, key_points, decisions, action_items}
REDUCE：所有局部 JSON（已压缩，非原文）一次合并 → 最终纪要 JSON
       局部 JSON 过多 → 分层树状归并（每 5~8 个一组，多级 reduce）
```

**单主题长会可选**：有界 Refine —— 用关键词 top-k 召回"已抽取要点"替代全量滚动摘要，避免漂移膨胀（同 pico 记忆检索思想）。

**容错**：单段 MAP 失败重试 2 次，仍失败标记"该时段转写质量低"跳过，不阻塞全局（搬福客 judge retry + extractJSON 三级容错）。

**最终纪要 schema（待按业务补字段）**：
```json
{
  "meeting_title": "", "participants": [], "agenda": [],
  "topics": [{"topic":"","summary":"","key_points":[]}],
  "decisions": [], "action_items": [{"task":"","owner":"","due":""}],
  "risks": []
}
```

## 八、P1：专名纠错（LLM + 分层术语库 RAG + 拼音 + 判定）

**本质**：ASR 把专名转错（气瓶→器皿），用外部术语库检索正确候选并纠正。这是 RAG 模式——把不该塞进参数的知识外置成可维护知识库。

**完整纠错链（RAG 只是骨架，拼音匹配和 LLM 判定是补充的两块）**：
```
主题识别（LLM，意图）
  → 按主题加载领域包（检索，确定性）
  → 拼音/编辑距离找可疑词（模糊匹配，RAG 补不了这步）
  → LLM 结合上下文判定是否替换（防过度纠正）
  → 纠错后文本 → 总结
```

**端侧要点**：
- **广义 RAG（关键词/拼音检索），非向量 RAG**——向量 RAG 要额外 embedding 模型，吃 NPU/内存，违背纯板端约束（同 pico "不引入 embedding" 取舍）。
- **实现选程序化编排，非 agentic function-calling**——端侧 4B function-calling 不稳；让模型判语义、代码精确查表注入，各司其职。
- **鸡生蛋兜底**：主题识别基于已错的 ASR 文本，靠上下文鲁棒性；判不准就退到"整场会议域"粗粒度兜底。

**术语库分层结构**：
```
核心通用层（常驻，~300-800 词）：会议通用词 + 高频跨行业黑话
领域包（按需/按部署下发，每包 ~500-2000 词）：安全/财务/光机/互联网增长…
自增长层（从本组织历史纪要自动挖）：极米内部代号、项目名、人名
```
- 实际每台设备只需 核心 + 1~3 领域包 ≈ 1000~3000 词，不是全行业十几万。
- **体积不是约束**（十几万词也才几十 MB，远小于模型文件）；真正成本是**精修维护 + 检索精度**，故不追求大而全，用分层 + 按需加载（索引/分区裁剪思想）。

**术语库来源（模型能给通用、给不了私有）**：
- 大模型**离线**生成通用术语库草稿（4B 端侧生成不可信，幻觉高；生成属开发期任务，不放运行期）。
- 人工补**企业内部专名/代号/人名**（模型不知道，是产品真正壁垒）。
- 从历史纪要**自增长**回填（派生式提取）。

## 十一、待确认清单（去问 leader / 工厂验证）

**最关键两项**：
1. **固件分给会议助手的内存预算** —— 决定端侧能否装下 ASR+LLM，否则走"算力外移"。
2. **投影仪麦克风阵列的远场多人收音质量** —— 开发板用的是干净录音（`L_R004S06C01`），真机远场嘈杂可能让 diarization 大幅退化。

**其余**：
3. 投影仪 SoC/NPU/内存是否与开发板同款？
4. 板端 Qwen3-4B 的 `max_context_len`（定 P0 所有切分数字）？
5. 投影仪还并发跑哪些 AI（NPU 到底多空）？
6. 会后处理时风扇噪音可接受吗？有无静音时段限制？
7. 处理时机：会议结束自动触发 or 用户手动？待机能否唤醒？
8. 音频/纪要存储位置、留存时长、隐私合规？
