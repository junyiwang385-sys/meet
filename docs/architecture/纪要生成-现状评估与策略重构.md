## 二、当前纪要策略的问题评估

采样参数（`main.py`）：`temperature=0 / server_temp=0 / top_k=1 / top_p=1` —— **纯贪心解码**，输出确定可复现。

### 2.1 章节划分任意（不是随机，是语义任意）
- 贪心解码下不存在 RNG 抖动；"随机"的本质是**语义任意性**：输入稍变（多一句寒暄、ASR 错一词），边界大幅漂移。
- 根因：让 4B 直接输出 `core_start_ref`/`core_end_ref` 这种**精确 segment ID 当章节切点**，这是话题分割里最难的一种形式。话题边界本身模糊，4B int4 内部没有稳定信号支撑离散边界决策 → 边界必然任意。
- **ref 一符两用**：`rN` 既是"引用证据"又是"章节分界"，两种语义互相干扰。
- 提示词要求"结论方向变化必须新建章节"——要 4B 在长时间轴上跟踪元认知信号，做不到。
- **校验层救不了**：`validation.py` 只查结构（refs 存在、`start_ms ≤ end_ms`、无占位词）；`_normalize_overlapping_core_candidates` / `_expand_core_chapter_ranges` 那套修复**只修区间重叠/逆序/越界，从不判断切点语义对不对**。这套修复机器的存在，本身就是"原始输出不可靠"的证据。

### 2.2 摘要字数少（软约束零强制）
- `validation.py` **无任何长度校验**：`clean_text` 只做去空白 + 占位词过滤，`normalize_summary` 全程不看字数。"约 300-500 字"纯属提示词许愿，给 80 字也照样 `status: pass`。
- 放大因素：贪心解码（top_k=1）天然偏短；int4 量化最先丢的就是"字数/句数"这类软指令遵循；单请求多目标稀释注意力。
- 提示词里"overview.refs 不要只引用开场的一段"是**已踩过 lost-in-the-middle 的补丁痕迹**。

### 2.3 单请求 `single_request_all_features` 在 4B+int4 下不可行（作为质量主路径）
- `plan["full_request_fits"]` 为真时走单请求，让 4B 在**一次前向**里同时完成：话题分割 + 精确边界 ref + 多段摘要 + 发言人归因 + 待办抽取，输入是整场时间轴。
- 对 4B int4 是几乎不可能稳的复合结构化任务：长输入注意力稀释 + lost-in-the-middle；多层嵌套 JSON + 大量精确 ref → 坏 JSON/幻觉 ref/截断风险叠乘；int4 让每项失败率再上台阶。
- smoke 能过是因为测的是干净短音频；真实 1-2h 长会这条路的分割质量与 overview 丰度都会崩。
- **自相矛盾**：项目另一条 `sliding_chapter_windows` 明明是解耦的 map-reduce（架构对），单请求却把它塞回一个请求，违背了自己的 map-reduce 原则。

### 2.4 "直接通过提示词生成" —— 核心设计气味
章节划分 100% 委托 4B 徒手生成，零算法先验。话题分割恰恰最该给模型**脚手架**，而不是让它凭空发挥。

## 三、目标方案：确定性四层流水线

**核心思路：把"话题分割"从模型手里拿走一部分，让模型只做它擅长的"给定一段文本写摘要 / 做二分类判断"。智能放在 Python 的 DAG 里，不放在模型的自主决策里。**

### A 层｜确定性话题分割（CPU，无 LLM）
- 用前半链路本来就有的信号做切点：speaker 切换点（已有）、VAD 长静音 gap（已有），叠一个 ASR 文本上的轻量词汇内聚度 / 滑窗话题漂移打分（TextTiling 思路，纯 CPU）。
- 产出一串**候选块（block）**，受 token 预算约束。**宁可过切**——A 层只保证"切得不漏"，语义合并交给后面。
- 这一步直接消灭"边界任意"：边界不再由模型凭空生成。
- 架构文档里"speaker切换 → VAD gap → 句末标点"的确定性切分器，本就该前置到 LLM 之前，A 层把它接回来。

### B 层｜逐块处理（NPU，map，一次调用一职）
- 每个 block 一次 LLM 调用，**只干一件事**：总结成 `{title, summary(200-400字), key_points, refs}`。小而聚焦 → 4B 稳、肯写长、JSON 不崩、字数好强制。
- 叠一个模型能可靠做的**微决策**替代徒手分割：给相邻两块问"是否延续上一块话题？yes/no"（二分类，4B int4 做得了），用它合并 A 层的过切 —— 这是"模型辅助分割"而非"模型发明分割"。

### C 层｜归并（reduce）
- 相邻同话题块合并 → 最终章节。
- 各块摘要 reduce → 全文 overview（滑窗路径 `_full_summary_messages` 已这么做，保留）。
- 发言人：按 speaker 分组，逐人/分批一调用（已有，保留）。
- 待办：逐块抽取 → 一次去重复核（已有，保留）。
- **overview 永远走 reduce 侧生成**，不再由单请求顺带吐——这是它现在写得薄的直接原因。

### D 层｜校验 + 落盘（+ 可选自检）
- 保留现有 grounding 校验（refs 必须存在、owner/deadline 无依据即清空）——全项目最值钱的部分，别动。
- **补长度门 + 触发重试**：overview/章节摘要低于阈值，像现在处理坏 JSON 一样受控重试（重试框架现成）。
- 可选一个 "critic" 节点复查幻觉/覆盖度，但**固定一次调用，不做循环**，默认关闭，等有 golden set 再评估。

## 四、Agent 边界判断

**纪要生成本身必须是确定性工作流，不引入自主 Agent。** 理由：

1. 必须确定性 + 可断点续跑：现有 resume 靠 `config_identity` / `request_fingerprint` 指纹复用，依赖请求图稳定；Agent 动态规划会让指纹复用、幂等、golden set 回归全部失效。
2. 4B int4 的 function-calling / planning 不可靠（架构文档 P1 已有此判断）。
3. 离线批处理 + 单 NPU，任务图先验已知，没有"临场决定调哪个工具"的场景；Agent 动态编排纯增开销与延迟。
4. 可观测/可调试：固定 DAG + 每节点 artifact 才能逐节点校验回归；Agent trace 在 4B 上既不稳又难复盘，与现有 runlog/artifact 体系冲突。

**Agent 真正的位置在未来的交互层**：对生成好的纪要做多轮追问/问答（RAG-over-minutes），数据源固定、工具明确、失败可容忍，值得做。

若为叙事需要把 B/C 层专职 LLM 节点称作"角色化 agent"，前提是它们**无状态、单轮、代码调度**——区别只在措辞，不在架构。

## 五、改造 checklist（保留 vs 改）

| 现有 | 处置 |
|---|---|
| 窗口 map-reduce 骨架（sliding_chapter_windows） | 保留并升级为主路径 |
| `single_request_all_features` | 降级为"极短单主题会"快路径，不再承载质量 |
| 让模型吐 `core_*_ref` 当切点 | 删掉，换成 A 层确定性切点 + B 层 yes/no 合并 |
| grounding 校验 / resume 指纹 / 受控重试 | 全保留（资产） |
| 无长度校验 | 补上，进重试环 |
| overview 由单请求顺带产出 | 改为永远 reduce 侧生成 |

**优先级建议**：A 层确定性分割的信号融合（block 边界）是整个方案的胜负手，先敲定；其次 B/C 解耦分割与摘要 + D 层长度校验重试。P1 专名纠错作为独立确定性 RAG 层，接在 ASR 与摘要之间，最后并入。
