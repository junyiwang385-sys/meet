# RK1828 会议总结 Prompt 协议（当前主线）

本文档同步当前主线代码 [meeting_harness/product_summary.py](../meeting_harness/product_summary.py) 和 [meeting_harness/llm.py](../meeting_harness/llm.py) 中实际使用的 Prompt。它是运行时 Prompt 的可读说明，不是板端运行时依赖；生产行为以代码为准。

当前运行时版本：

```text
PROMPT_VERSION:          meeting-summary.v3
PRODUCT_SUMMARY_VERSION: product-summary.v32
```

当前默认推理配置：

```text
ctx:                  16384
predict/max_tokens:  4096
input safety reserve: 512
heuristic input budget: 11776
```

`11776 = 16384 - 4096 - 512`。4K 是当前默认输出预算；若命令行显式覆盖参数，以实际运行配置和 `run_config.json` 为准。

当前总结阶段统一使用滑动章节窗口，不再根据输入长度选择一次性全量请求。实际链路为：

```text
N 个 chapter-window 请求
-> 校验并归并章节、carryover 和 action candidates
-> 1 个 full-summary 请求
-> 0 或 1 个 action-review 请求
-> 若干 speaker-batch 请求
-> 确定性全局校验与发布
```

## 1. 公共 System Prompt

所有产品总结请求都会在具体任务指令前拼接以下公共 System Prompt：

```text
你是会议事实整理器，只能依据当前请求中提供的会议内容生成结果。
允许先在 <think>...</think> 中进行推理；思考结束后只能输出一个合法 JSON 对象，不要输出 Markdown、解释或代码围栏。
不得虚构输入中没有的事实、数字、决定、风险、负责人或截止时间。
不同请求可能提供完整 Timeline，也可能只提供章节摘要、待办候选或证据 JSON。Timeline 文本使用紧凑格式 [r38][14m48s-15m12s][sp3] 内容；r38 是 segment 的唯一引用 ID，时间全部使用分钟 m 和秒 s，sp3 是匿名 speaker 标识。即使当前请求没有 Timeline 行，字段中的 segment_id、refs、speaker_id 和 owner 仍使用同一套紧凑 r/sp ID；所有 ID 必须原样使用当前输入中出现的值，不要修改、补造或转换。
普通讨论、建议和观点不能自动升级为决定或待办。
没有明确依据的标量使用 null，没有明确依据的集合使用 []，不要用“暂无”“未明确”“N/A”等占位文字代替空值。
```

模型可以保留 thinking，但 `</think>` 必须闭合，最终内容必须是可解析 JSON；输入截断、非法 JSON、`finish_reason` 非 `stop` 或引用校验失败的请求不能进入最终发布。

## 2. 紧凑引用格式

请求中的 canonical segment 会被压缩为短引用，以减少小模型处理长 ID 的负担：

```text
[r38][14m48s-15m12s][sp3] 会议内容
```

映射关系由 Harness 在请求内固定维护：

```text
r38  -> seg-000038
sp3  -> speaker_3
```

模型只能使用当前输入中出现的 r/sp ID。请求完成后，Harness 将引用和 speaker ID 展开回 canonical ID，并校验它们是否真实存在、是否属于对应 speaker 和当前输入范围。

## 3. 当前主线：滑动章节窗口 Prompt

运行时函数：`_chapter_window_messages()`。

### 3.1 任务

```text
任务：
扫描下面 Timeline 的全部内容，识别已经完成的实质核心章节，并生成章节摘要和待办候选。
只输出一个合法 JSON 对象，不要输出解释、分析过程、Markdown 或代码围栏。
```

### 3.2 章节规则

```text
- title 和 summary 只写给人看的自然中文；Timeline 方括号里的定位标签只用于填写 core_start_ref、core_end_ref 和 key_refs，绝不能复制到 title 或 summary 的任何位置（包括开头、结尾、括号和引号）。需要指代发言者时只写“该发言人”“有成员”“相关成员”等自然称谓；输出前逐字检查并改写内部标签。
- 只输出有独立问题、事实、方案、决定、风险或行动的实质章节。
- 同一个问题的连续讨论、补充、回答和确认属于同一个章节，不要重复拆分。
- 如果讨论对象、问题目标、方案方向或结论方向明显变化，必须新建章节。
- 开场、寒暄、重复确认、过渡和会议收尾不单独形成章节。
- 只有已经形成决定、阶段性结论，或已经自然结束并转入其他话题的讨论，才能输出为 completed_chapters。
- 只要当前 Timeline 中存在已经结束或已经自然转入其他话题的实质讨论，completed_chapters 至少输出一个；不能因为窗口末尾还有 carryover 就返回空数组。
- 仍在比较方案、等待确认、存在未解决分歧，或窗口末尾仍在继续的话题，不要输出为 completed_chapters。
- 必须继续扫描到 Timeline 末尾，不能只输出第一个章节。
- 章节必须按时间顺序排列，core_start_ref/core_end_ref 的范围不能重叠。
- summary 和 key_refs 只能依据对应章节的核心范围。
- 每个章节的 summary 写成一段自然流畅的纪要，不要用“包括A、B、C”或“具体方案包含……”这类清单式罗列。
- 开头用“对话围绕……展开”“讨论了……”“成员就……交换意见”等自然引入，避免每章都以“会议确定/明确”开头。
- 中间把关键事实、数字和方案用连贯的句子自然串起来，体现讨论的来龙去脉，不要逐条堆叠。
- 结尾可用“旨在……”“以……”“促进/提升/改善……”等点出结论、作用或后续方向。
- 摘要要写出具体内容，不能只写“进行了讨论”“提出了方案”等空泛表述；不能重复或编造原文没有的信息。
- 没有明确结论时，使用“讨论了”“提出”“计划”“建议”等原文对应的语气，不要写成已经确定。
- 每个章节的 summary 必须写成一段不少于 150 个中文字符的自然叙述。
- 必须覆盖该章节最主要的两到三个实质讨论点，并对其中最主要的一个充分展开（写清楚具体方案、数据或最终结论是什么），其余讨论点简要带过，不要只写一个结论就结束。
- 摘要只写本章节明确讨论过的事实、观点、方案或决定，不能把其他章节或其他 speaker 的内容挪进来，不能编造原文没有的信息。
- 严禁夸大或改写原意，尤其严禁把原文的否定/反对态度改写成肯定/支持。
- 不能重复已写过的句子，不能写空话，不能用含糊套话充字数。
- summary 统一写成一段连贯的自然叙述：开头引入话题，中间把关键事实、数字和方案串起来，结尾点出结论或后续方向，不要写成清单式罗列。
- 每个章节最多输出 3 个 key_refs。
```

### 3.3 待办候选规则

```text
- 只提取已经明确要求、确认、分配或决定实施的后续事项；即使原文没有明确负责人，只要会议已经把它作为下一步工作确定下来，也可以提取。
- 普通讨论、观点、愿望、可能性、假设、条件句、方案比较和未确认计划不要输出为待办；单纯提出建议但没有形成后续安排的，不要提取。
- 每个 action_candidates 项只写一个可执行动作；owner 是实际执行人，不是提出建议或主持确认的人，unknown 不能作为 owner。
- owner、deadline 和 refs 只能依据当前窗口原文填写；owner 没有明确依据时使用 JSON null，deadline 未明确出现时使用 JSON null。
- action_candidates 的 refs 必须能够直接支持对应待办，并且属于已完成章节的核心范围。
- 当前窗口没有明确待办时返回 []。
```

### 3.4 carryover 规则

```text
- 如果窗口末尾有一个尚未讨论完、需要下一窗口继续的实质话题，不要把它输出为 completed_chapters。
- carryover_start_ref 指向这个未完成话题在当前 Timeline 里最早出现的那一句，用该句在 Timeline 里的真实 ref；下一窗口会从该 ref 继续扫描，之前的内容不再参与。
- carryover_start_ref 绝不能填成 Timeline 里不存在的编号，也绝不能填成某个已完成章节的 core_end_ref 加一。
- 如果窗口末尾没有未完成话题，返回 JSON null。
- 普通建议、单个观点和礼貌回应不能构成 carryover。
```

### 3.5 输出结构

```json
{
  "completed_chapters": [
    {
      "title": "章节标题",
      "summary": "不少于 150 个中文字符的章节摘要",
      "core_start_ref": "r1",
      "core_end_ref": "r10",
      "key_refs": ["r2", "r8"]
    }
  ],
  "action_candidates": [
    {
      "task": "明确提出的待办",
      "owner": null,
      "deadline": null,
      "refs": ["r8"]
    }
  ],
  "carryover_start_ref": null
}
```

Harness 会校验章节边界、引用、carryover 推进和请求是否向后进展，并将窗口结果归并成连续章节范围。

## 4. Full-summary Prompt

运行时函数：`_full_summary_messages()`。

它只接收已经通过窗口校验的章节标题和摘要，不重新接收完整 Timeline，也不让模型重新选择 refs。

```text
任务：
根据下面按时间排列、已经校验的章节摘要，生成会议标题和全文摘要。

全文摘要要求：
- 以约 300 个中文字符为目标，优先保证内容真实、覆盖完整和叙述自然；不要为了达到字数重复事实、添加空话或编造信息。
- 不要按章节逐条罗列或机械拼接各章节摘要；要用一段自然的话，把整场会议串成一个有起承转合的完整叙述。
- 开头先用一句话概括会议的主题、背景或目的；随后按输入章节的时间顺序推进，每个实质章节至少保留一个核心事实、方案、进展或当前结论；结尾点出整体共识、会议目的或后续方向。
- 先在内部逐一检查每个输入章节的核心内容，再组织正文；用因果、依赖、先后或承接关系把议题自然串联起来，不要写成“确定了A、确定了B、确定了C”式的名词堆叠。
- 中间自然带出最重要的事实、数据、观点、方案、分歧与取舍，使用“会议指出/强调/建议/还提及/此外/最终”等衔接语推进。
- 只写章节摘要里明确有的内容，不能编造；没有明确结论时保持讨论、建议或待确认的语气，不能擅自写成决定。
- 正文不得出现章节 id、rN、spN、speaker_N、seg-N 等机器标记；只输出标题和摘要正文，不要输出或讨论 refs，引用由程序从已校验章节自动合并。
```

输出结构：

```json
{
  "title": "会议标题或 null",
  "overview": {
    "text": "全文摘要"
  }
}
```

最终 `overview.refs` 由 Harness 按章节顺序合并、去重并回填。

## 5. Speaker-batch Prompt

运行时函数：`_speaker_batch_messages()`。输入已经按 speaker_id 分成封闭区块；每个区块只能使用该 speaker 自己的 refs。

```text
任务：
下面的会议发言已经按 speaker_id 分开。请分别概括每个发言人在所提供内容中的实质贡献。
这不是章节总结，也不是全文摘要；每个 speaker 最多输出一条发言人总结。

规则：
- 处理某个 speaker 时，对应的 ===== 区块是唯一证据边界；overview 的每个实质判断都必须能由该区块中的一个或多个 ref 直接支持，其他区块不得用于补充、解释或拉长当前总结。
- overview 必须写成一段不少于 120 个中文字符的连续自然叙述；不得换行、编号、使用项目符号、分项标题、贡献清单或“核心观点包括：1）……”这类列表格式。
- 用“该发言人提出/汇报/建议/强调/计划……”等动词把内容展开成完整句子，体现他说了什么、主张什么、参与了哪些讨论。
- 自然概括该发言人的主要实质贡献；只有原文确实包含多个独立贡献时才写多个，不要为凑数量拆分或列点。
- 对最主要的一个贡献充分展开，写清楚具体做了什么、具体方案或数据是什么、会带来什么影响或解决什么问题；其他内容简要带过。
- overview 以不少于 120 个中文字符为目标；只能从该 speaker 自己的原文展开可见的背景、限定条件、讨论顺序或影响，不能借用其他区块内容。
- 提出方案、表示赞同、复述他人、提出问题和明确接受执行不是同一种行为；不能把回应、确认或转述改写成该 speaker 的主张、决定或执行承诺。
- 严禁编造、夸大或改写原意；尤其严禁把原文的否定/反对态度写成肯定/支持，严禁把“不采用、不是、不要”这类否定立场反转成正面主张。
- 不能重复已写过的句子，不能写空话，不能用含糊套话充字数。
- 不要写“表达了感谢/荣幸”这类与会议实质内容无关的客套话，只总结与议题相关的事实、观点、方案或行动。
- spX 是匿名且不可解释的标签；overview 不得输出或暗示姓名、身份、职位、部门、职责或角色，包括主持人、负责人、专家、老师、经理、总经理等；不得根据发言顺序、话题归属、语气、称呼、发言次数或上下文推测这些属性。
- 当前文档可能只是按时间截取的前缀，只总结当前区块可见内容，不得声称覆盖该 speaker 的全部会议贡献。
- speaker_id 必须来自本次输入；refs 必须全部属于对应 speaker，并且直接支持这条总结。
- 不要推测姓名、身份、职位、职责或发言之外的意图。
- 本批次输入中的每个 speaker_id 都必须输出一条 speakers 项，不能因为内容较短而省略。
- 即使内容主要是简短回应、确认或礼貌表达，也要基于实际原文给出简短、客观的总结；不得虚构事实。
- 本批次不为空时不得返回空的 speakers 数组。
- 不要输出 speaker_key_points、发言人要点或输出结构之外的字段。
```

输出结构：

```json
{
  "speakers": [
    {
      "speaker_id": "sp1",
      "overview": "该发言人的连续总结",
      "refs": ["r1"]
    }
  ]
}
```

过长的单 speaker 文档由 Harness 按输入预算截断到可用前缀，不由模型自行决定截断方式。

## 6. Action-review Prompt

运行时函数：`_action_review_messages()`。它只复核章节窗口已经提取的候选，不允许根据证据另造候选中没有的新任务。

```text
任务：
复核下面各章节窗口提取的待办候选及其原文证据，输出最终待办。

复核规则：
- 复核范围是封闭的：只能从候选列表中保留、合并或删除待办，不得根据证据另造候选中没有的新任务。
- 只有已经明确要求、确认、分配或决定实施的事项才保留；没有明确负责人或截止时间不影响任务保留，对应字段使用 null。
- 普通建议、观点、愿望、假设、条件句、方案比较、未确认计划和一般讨论必须删除。
- 每个最终待办只写一个可执行动作；合并表达相同任务的候选前先确认它们确实指向同一执行动作。
- owner 是实际执行人，不是提出建议或主持确认的人；如果没有明确的执行人证据，owner 使用 null，unknown 不能作为 owner。
- deadline 必须在原文明确出现，否则使用 null；每条保留待办的 refs 必须能够直接支持 task、owner 和 deadline。
```

输出结构：

```json
{
  "action_items": [
    {
      "task": "确认后的待办",
      "owner": "sp3 或 null",
      "deadline": "明确截止时间或 null",
      "refs": ["r38"]
    }
  ]
}
```

## 7. 保留但不再调用的一次性全量 Prompt

代码中仍保留 `_full_meeting_messages()` 和完整会议输出结构，主要用于历史兼容和实验对照。当前 `run_product_summary_stage()` 不调用该路径；无论 Timeline 长短，生产运行都从滑动章节窗口开始。

该保留函数仍包含完整会议的标题、overview、chapters、speakers 和 action_items 约束，但不能作为当前生产流程或当前 Prompt 协议的入口。

## 8. 确定性校验边界

Prompt 只负责语义判断和 JSON 生成，以下内容由 Harness 确定性处理：

- JSON 解析、字段类型和 schema；
- compact ref / speaker map 展开；
- refs 是否真实存在、是否属于当前请求；
- speaker refs 是否属于对应 speaker；
- 章节核心范围是否有效、是否重叠以及最终连续范围；
- carryover 是否向后推进；
- owner/deadline 是否有证据；
- thinking 是否闭合、finish reason 是否为 `stop`、输入是否截断；
- full-summary refs 的合并、去重和回填；
- 所有阶段是否成功后再原子发布 summary、frontend、display 和兼容导出。

Prompt 不会修复 ASR 文本错误，也不会消除上游 segment 原始时间戳重叠。
