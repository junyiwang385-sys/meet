## 2. 执行摘要

### 2.1 市场已经形成的基础能力

【横向矩阵事实】云端竞品普遍已经覆盖录音或上传、转写、时间轴、说话人、摘要、章节、编辑、回放、分享等基础能力；腾讯会议和 Teams 在会议平台链路、导航和权限方面较完整，飞书和钉钉具有组织协作基础，科大讯飞提供离线/私有化方向，MAXHUB提供固定会议室的大屏、触控、麦克风和摄像头硬件形态。

因此，本产品仅提供“录音＋转写＋摘要”不足以构成明显差异，这些能力只能作为进入市场的基础门槛。

### 2.2 当前竞品证据中的共同空白

【横向矩阵事实】六家竞品在本轮资料中均未确认以下完整闭环：

1. 会尾在共享大屏上由参会者共同核对关键结果；
2. AI草稿经主持人或授权人员确认后才成为正式纪要；
3. 正式纪要记录确认人、确认时间、版本和分发范围；
4. 每条决策和行动项独立关联原始发言证据；
5. 责任人、截止时间缺失时明确提示而不是AI自行补全；
6. AI行动项经确认后进入组织任务系统并持续回写执行状态；
7. 音频、转写、AI草稿和正式纪要分层保存、删除和审计；
8. 从采集、转写、提取到保存和导出的完整端侧断网闭环。

### 2.3 建议的产品定义

【产品分析/合理推断】建议将产品定义为：

> **面向敏感企业固定会议室的端侧会议执行与治理终端：在明确授权下本地完成会议理解，在会尾帮助所有参会者共同确认决策和行动项，并生成可追溯、可治理、可受控流转的正式纪要。**

该定义的中心对象不是逐字稿，而是经过共同确认的“决策、行动项和正式纪要”。

### 2.4 建议的差异化主轴

```text
明确授权与持续可见状态
  → 全链路本地处理
  → 结构化决策与行动项
  → 条目级原始证据
  → 会尾大屏共同核对
  → 授权人员正式确认
  → 分层保存、删除与受控分发
  → 后续行动状态闭环
```

## 3. 竞品普遍具备、本产品必须补齐的基础能力

| 基础能力 | 横向事实 | 对本产品的最低要求 | 建议优先级 |
|---|---|---|---|
| 会议音频采集或导入 | 多家软件竞品支持会议录音、上传或平台录制；MAXHUB提供会议室采集硬件 | 支持目标固定会议室的阵列麦克风采集；是否支持文件导入可作为补充入口 | P0 |
| 普通话转写 | 软件竞品普遍具有转写方向，但只有飞书有单次无Gold样例 | 断网完成普通话转写，并支持快速人工修正 | P0 |
| 时间戳和音频回放 | 飞书、讯飞、腾讯、Teams有不同程度的时间轴或回放 | 转写片段必须保留稳定时间定位，并能回放对应音频 | P0 |
| 发言人分段 | 多家竞品已有说话人或声纹方向，真实效果均未形成横向质量结论 | 至少区分发言段；不确定边界必须显式标记并允许快速纠错 | P0 |
| AI摘要/智能纪要 | 云端软件竞品普遍具备 | 生成结构化草稿，但不得直接成为正式纪要 | P0 |
| 人工编辑 | 多家竞品具备文本、纪要或协作页面编辑 | 决策、行动项、责任人、截止时间和证据均可在会尾直接修改 | P0 |
| 基础导出和分享 | 多家云端竞品具备分享或导出，但数据边界不同 | 首版至少提供本地受控导出；普通公共链接分享不作为默认方案 | P0 |
| 权限和组织角色 | 腾讯和Teams较明确，其他竞品有不同程度组织权限 | 至少区分设备管理员、主持人/确认人和普通参会者 | P0最小权限＋P1完整角色体系 |
| 企业术语 | 腾讯和Teams有较明确词库方向，讯飞和钉钉有局部证据 | 首版可保留接口和数据结构，企业词库管理建议在试点阶段增强 | P1；若首批样本证明术语错误严重可前移 |
| 章节、AI问答、实时字幕、多语言 | 多家竞品已经提供或宣传 | 属于市场可见能力，但不构成本产品首版核心闭环 | P2或后续验证 |

### 基础能力结论

1. **转写、说话人、摘要、编辑和回放必须达到“可用门槛”，但不应成为唯一卖点。**
2. **时间戳不等于证据闭环。**本产品需要把时间戳升级为“结构化条目—发言人—时间点—原文—音频”的可核验关系。
3. **分享不等于安全流转。**本产品应优先做受控导出和局域网分发，而不是复制公共云链接分享。
4. **任务入口不等于行动闭环。**责任人、截止时间、确认和状态回写必须分别定义。

## 4. 不宜直接照搬的云端产品设计

| 云端常见设计 | 不宜直接照搬的原因 | 本产品建议 |
|---|---|---|
| 上传或云录制后再生成纪要 | 与“不希望会议内容上传外部云端”的目标场景冲突 | 录音、ASR、说话人、摘要和证据索引默认全部本地运行；联网能力默认关闭或独立授权 |
| 以账号、云盘或公共链接为内容中心 | 容易将会议内容纳入外部账号、云存储和分享链路 | 以会议室设备、本地会议对象和受控分发范围为中心 |
| AI摘要生成后直接分享 | AI结果可能包含误解、遗漏或编造，不能等同正式纪要 | 所有AI结果先进入草稿，必须经过会尾核对和授权确认 |
| 完整逐字稿作为主要结果页 | 会尾时间有限，长文本不适合多人共同确认，也可能在大屏暴露不必要内容 | 大屏默认只展示决策、行动项、待确认问题和关键证据；逐字稿按需展开 |
| 自动创建组织任务 | 责任人或截止时间识别错误会把AI错误直接扩散到执行系统 | 只有“已确认”的行动项才能创建或同步任务；同步失败不得影响本地正式纪要 |
| 把任务系统存在视为行动闭环 | 多数公开资料没有证明AI提取、确认、创建和状态回写全链路 | 明确定义“提取—补字段—共同确认—创建—回写—关闭”六个阶段 |
| 用云端保留策略替代本地生命周期 | 云端Hold、回收站和对象继承逻辑复杂，可能不符合设备端的即时删除预期 | 音频、转写、草稿和正式纪要分别配置保留期限，删除结果可见且可审计 |
| 默认绑定厂商生态和复杂许可 | 会增加采购、账号、地域、运维和持续费用不确定性 | P0保持单机可闭环；外部日程、任务和文档系统作为可选连接器 |
| 默认开启声纹或人脸实名识别 | 会增加生物特征数据治理和员工接受度问题 | P0优先采用参会人预录入＋会后标注；声纹作为受控、可撤销的P1能力 |
| 将实时字幕持续投到大屏 | 可能干扰讨论，并扩大敏感内容的现场暴露 | 实时字幕不作为默认界面；会尾确认才是大屏核心模式 |

## 5. 可形成端侧本地产品差异化的能力

### 5.1 差异化一：可证明的全链路本地处理

【产品分析/合理推断】“本地”不能只指音频保存在设备上，而应至少覆盖：

- 音频采集；
- 普通话ASR；
- 说话人分段；
- 摘要、决策和行动项提取；
- 条目级证据索引；
- 会尾编辑和确认；
- 正式纪要保存；
- 删除、导出和审计。

建议产品界面持续显示：当前是否联网、会议数据是否离开设备、录音状态、静音状态、当前处理阶段和存储位置。

### 5.2 差异化二：会尾共同确认

MAXHUB证明了大屏、触控和会议室协作的硬件形态基础，但本轮竞品资料没有确认完整会尾正式确认流程。【横向矩阵事实】

建议把会议结束前1～3分钟设计为独立产品阶段：

1. 仅展示决策、行动项和待确认问题；
2. 突出责任人、截止时间、验收标准等缺失字段；
3. 点击任一条目可核对原始证据；
4. 现场修改后标记差异；
5. 由主持人或授权人员执行最终确认。

其中“1～3分钟内能完成”仍是【待真实用户验证】的假设，不能直接冻结为发布指标。

### 5.3 差异化三：行动项闭环而不是待办列表

建议行动项至少包含：

| 字段 | P0处理原则 |
|---|---|
| 行动内容 | 必填；来自明确发言或会尾人工输入 |
| 责任人 | 缺失时显示“待指定”，不得猜测 |
| 截止时间 | 缺失时显示“待确定”，不得根据常识补全 |
| 验收标准 | 可缺失，但必须单独显示，不混入行动描述 |
| 依赖项 | 可缺失；有明确证据时提取 |
| 原始证据 | 至少一个时间点、原文或音频片段；无可靠证据时标记“待核验” |
| 确认状态 | AI草稿、待确认、已确认分开 |
| 执行状态 | P0保留数据结构；跨会议持续回写建议P1 |

### 5.4 差异化四：条目级证据追溯

市场已有时间轴、章节和回放，但不能据此推断每条结构化结果都有独立证据。【横向矩阵事实】

建议每条决策和行动项保存：

```text
条目ID
＋结构化内容
＋发言人/候选发言人
＋开始与结束时间
＋原始转写片段
＋音频片段定位
＋模型置信/不确定状态
＋人工修改记录
＋最终确认记录
```

人工修改后应保留“AI原始草稿—人工修改—证据—正式结果”的关系，而不是覆盖后失去来源。

### 5.5 差异化五：正式纪要治理

建议采用以下状态模型：

```text
AI草稿 → 待确认 → 已确认 → 已发布/受控分发
                  ↘ 修订草稿 → 新版本待确认
```

正式纪要至少记录：

- 会议主题、时间、地点和参会人；
- 确认人、确认时间；
- 版本号；
- 保密等级和分发范围；
- 决策、行动项、待确认问题、风险和分歧；
- 每条关键结果的证据；
- 原始音频保留或删除决定；
- 导出、修改、删除和分发记录。

### 5.6 差异化六：分层数据生命周期

建议将以下对象独立管理：

| 数据对象 | 建议默认策略方向 | 用户控制 |
|---|---|---|
| 原始音频 | 会议确认后可选择立即删除或按短周期保留 | 主持人选择，管理员设置上限 |
| 原始转写 | 支撑证据核验；可与音频采用不同期限 | 可单独删除或脱敏保留 |
| AI草稿 | 未确认前不得对外作为正式纪要 | 自动过期或随正式版本归档 |
| 正式纪要 | 本地加密保存，遵循企业保留规则 | 按角色查看、导出、修订和删除 |
| 证据索引 | 与正式条目和原数据生命周期联动 | 原音频删除后应明确证据降级状态 |
| 审计记录 | 记录关键治理操作，不包含不必要会议正文 | 管理员按策略查询和保留 |

## 6. P0 建议：首版完整闭环

以下建议沿用当前P0-01～P0-09结构，但将其转换为后续PRD可直接展开的输入。所有性能数字仍需验证，不在本文件冻结。

| ID | 建议进入PRD的P0能力 | 首版边界 | 初始验收方向 | 证据状态 |
|---|---|---|---|---|
| P0-01 | 全链路本地、断网可用 | 核心会议数据默认不上传；外部连接器不影响单机闭环 | 断开公网后完成目标会议的采集、转写、提取、确认、保存和导出；检查无非授权外发流量 | 需求强假设；可行性待原型实测 |
| P0-02 | 授权录音、物理控制和持续状态提示 | 未授权不得开始；静音和停止必须立即生效 | 新用户无需培训即可识别录音/静音/停止状态；所有状态变化有明确反馈 | 需求假设；待用户与硬件验证 |
| P0-03 | 离线普通话转写和快速纠错 | 首版聚焦普通话、3～15人、固定会议室 | 建立脱敏Gold后评估人名、术语、数字、日期和关键语句；指标TBD | 无统一竞品质量结论；待Gold测试 |
| P0-04 | 基础发言人分段和不确定边界 | 不承诺复杂重叠发言和完美实名识别 | 关键决策/行动项发言人归属可核对；不确定归属不得静默写错 | 多家竞品有方向；真实效果待测 |
| P0-05 | 结构化AI草稿与防编造 | 摘要、决策、行动项、责任人、截止时间、验收标准、风险、分歧和待确认项分别建模 | 无证据或字段缺失时明确标记；任何未经确认的AI结果不得成为正式事实 | 市场有局部能力；完整字段闭环未确认 |
| P0-06 | 会尾大屏共同核对和修改 | 默认展示关键结果，不默认展示整篇逐字稿 | 关键字段可直接编辑；缺失项醒目；支持查看证据；确认耗时目标待用户验证 | 竞品共同空白；MAXHUB仅证明硬件形态 |
| P0-07 | 主持人确认和正式纪要状态 | AI草稿、待确认、已确认、已发布分开；确认后修订生成新版本 | 正式纪要包含确认人、时间、版本、分发范围；草稿不可误发为正式结果 | 竞品共同证据空白；治理需求明确 |
| P0-08 | 本地加密、分层删除和受控导出 | 音频、转写、草稿、正式纪要分别管理 | 可分别删除或保留；未授权用户不能导出；操作留下审计记录 | Teams提供云治理参考；本地实现待验证 |
| P0-09 | 决策和行动项的条目级证据 | 关键条目至少绑定时间点、原文或音频定位 | 一键从条目跳转到证据；无可靠证据时显示“待核验”；人工修改保留来源链 | 市场有时间轴基础；完整条目级链路未确认 |

### 6.1 P0应按三个不可拆分的质量门组织

| 质量门 | 包含需求 | 通过含义 |
|---|---|---|
| G1 安全与授权 | P0-01、P0-02、P0-08 | 用户明确知道是否录音、数据在哪里，并能控制停止、保存、删除和导出 |
| G2 内容可信 | P0-03、P0-04、P0-05、P0-09 | 关键结果可核对；不确定内容不被静默编造或归错 |
| G3 正式闭环 | P0-06、P0-07 | 参会者完成会尾核对，授权人员将草稿转化为可治理的正式纪要 |

任一质量门未通过，都不应把产品描述为已完成首版会议闭环。

### 6.2 P0暂不冻结的指标

当前需求表中的“决策准确率100%”“关键待办召回率≥95%”“AI编造为0”“3分钟内确认”等应保留为测试目标或安全原则，而不是未经Gold和用户试验就写入正式发布承诺。【待样例/设备实测】【待真实用户验证】

建议处理方式：

- “AI编造为0”保留为产品原则：任何无证据的内容不得自动进入正式纪要；
- 决策准确率、待办召回率先建立定义、Gold和样本分层，再冻结阈值；
- 会尾确认时长先进行可用性测试，再确定不同会议规模的目标；
- ASR、说话人和端到端时延按近场、远场、噪声、口音、术语和重叠发言分层评估。

## 7. P1 建议：企业试点和组织闭环

| ID | P1建议 | 建议理由 | 前移到P0的条件 |
|---|---|---|---|
| P1-01 | 本地企业词库 | 腾讯、Teams等已形成市场参照，制造研发企业术语密集 | 首批样本证明术语错误直接破坏决策和待办可信度 |
| P1-02 | 参会人、发言人和可撤销声纹管理 | 可减少固定项目组重复纠错，但涉及生物特征治理 | 不建议默认前移；P0优先预录入和人工标注 |
| P1-03 | 跨会议行动项跟踪 | 将产品从“生成纪要”延伸到“推动执行” | P0可保留单会执行状态，跨会议聚合仍放P1 |
| P1-04 | 完整角色权限和审计 | 企业采购需要管理员、主持人、参会者等权限边界 | P0必须有最小权限；复杂角色、策略和审计查询放P1 |
| P1-05 | 局域网受控分发 | 更匹配保密企业而非公共云链接分享 | 若首批客户禁止USB或要求内网流转，应前移 |
| P1-06 | 会前议程和上次待办 | 强化投影设备作为会议中枢的价值 | 不影响首版会后闭环，默认留P1 |
| P1-07 | 可配置的数据保留策略 | P0先支持分层删除；P1提供管理员策略、自动删除和审计 | 若首批试点有强制保留制度，应部分前移 |
| P1-08 | 单一日程/任务系统连接器 | 市场生态成熟，但直接照搬会扩大首版范围 | 仅在已确认任务可控、同步失败不丢数据时试点 |

P1的重点不是继续增加更多AI生成能力，而是把P0从单次会议闭环扩展为企业可管理、可分发、可持续执行的系统。

## 9. 建议的核心用户流程

### 9.1 会前

1. 主持人选择会议、保密等级和参会人；
2. 系统展示数据处理位置、联网状态和保存策略；
3. 参会者看到录音授权说明；
4. 未完成授权时，系统不得进入录音状态。

### 9.2 会中

1. 录音、静音和处理状态持续可见；
2. 本地完成转写和说话人分段；
3. AI在后台生成草稿和证据关系；
4. 会中不强制占用主屏展示完整转写；
5. 主持人可标记“这是决策”“生成待办”或“待确认”。

### 9.3 会尾

1. 系统自动进入“结果确认”界面；
2. 按决策、行动项、待确认问题和风险分区显示；
3. 缺失责任人、截止时间或证据的条目醒目标记；
4. 参会者共同核对，点击条目查看原话和音频；
5. 主持人修改、合并、删除或补全字段；
6. 授权人员确认并生成正式版本。

### 9.4 会后

1. 选择原始音频立即删除或按策略保留；
2. 正式纪要本地加密保存；
3. 按分发范围通过受控USB或局域网导出；
4. P1阶段将已确认行动项同步到任务系统；
5. 后续修改生成新版本，不覆盖原正式版本。

## 10. 建议的核心信息模型

| 对象 | 必要字段 | 关键规则 |
|---|---|---|
| Meeting | 主题、时间、地点、参会人、主持人、保密等级、授权状态 | 未授权不得录音；关联全部数据对象 |
| TranscriptSegment | 文本、开始/结束时间、发言人/候选人、不确定状态、音频定位 | 不确定说话人不得静默实名化 |
| Decision | 内容、状态、证据、确认人、修改记录 | 区分“建议/讨论”与“已确认决策” |
| ActionItem | 内容、责任人、截止时间、验收标准、依赖、证据、确认状态、执行状态 | 缺失字段显式保留，不得AI猜测 |
| OpenIssue | 问题、分歧、风险、下一步、证据 | 不得混入已确认决策 |
| MinutesVersion | 版本、状态、确认人、确认时间、分发范围、音频处理决定 | 已确认版本不可无痕覆盖 |
| EvidenceLink | 条目ID、片段ID、时间点、原文、音频定位、证据状态 | 原数据删除后更新可用状态 |
| AuditEvent | 操作人、时间、对象、操作、结果 | 记录确认、修改、导出、删除和权限变化 |

## 11. 会尾大屏交互的PRD输入

### 11.1 默认界面层级

```text
顶部：录音已停止｜本地处理完成｜当前联网状态｜保密等级

左侧：3项已确认决策
中间：5项行动项（2项缺责任人，1项缺截止时间）
右侧：2项待确认问题／风险

底部：查看证据｜返回修改｜主持人确认并生成正式纪要
```

### 11.2 交互原则

1. **关键结果优先：**默认不展示全部逐字稿；
2. **缺失字段优先：**责任人、时间和证据缺失应比普通文本更醒目；
3. **证据一步可达：**从条目进入原文和音频不超过一次主操作；
4. **共同可见：**修改结果立即在大屏更新；
5. **确认不可误触：**生成正式纪要需要明确确认人和二次确认；
6. **隐私最小展示：**涉及敏感个人信息或非必要原话时默认折叠；
7. **状态清楚：**草稿、待确认和正式版本在颜色、标签和操作上明确区分；
8. **不确定性可操作：**“待指定”“待确定”“待核验”都应能现场补全或保留。

## 13. 安全与治理的PRD输入

### 13.1 默认安全原则

- 默认本地处理和本地保存；
- 默认关闭会议内容外发；
- 所有联网、导出和同步行为均需独立授权；
- 录音必须有明确授权、可见状态和即时停止能力；
- 音频、转写、草稿、正式纪要和审计记录分别治理；
- 正式纪要只来源于已确认版本；
- 删除、导出和权限变更可追溯；
- 生物特征识别不作为默认必选能力；
- 设备遗失、磁盘拆卸、账户退出和恢复出厂需有数据保护策略。

### 13.2 需要后续确认的安全事项

1. 本地加密算法、密钥存储和密钥轮换方案；
2. 管理员、主持人和参会者的身份认证方式；
3. USB白名单、文件水印、有效期和撤回能力；
4. 局域网分发协议、客户端和访问控制；
5. 音频立即删除是否需要可验证擦除；
6. 模型、词库和软件升级是否需要联网，以及升级数据路径；
7. 日志中是否可能包含会议正文或敏感字段；
8. 目标行业需要的认证、等级保护或采购合规要求。

以上事项需要安全设计、原型验证和客户政策输入，不能仅根据竞品公开资料冻结。【待官方或商务确认】【待真实用户验证】

## 14. 不能直接作为P0承诺的证据缺口

| 证据缺口 | 当前状态 | 对PRD的处理建议 |
|---|---|---|
| 真实目标企业是否有高频“允许录音但拒绝上云”会议 | 当前主要是需求假设和虚拟输入 | 保留为目标市场假设，进入真实用户访谈第一优先级 |
| 会尾共同确认是否愿意执行 | 无真实用户数据 | 保留P0流程方向，但确认时长和完成率标TBD |
| 普通话ASR质量 | 仅飞书一个无Gold样例，其他竞品未测 | 建立本产品脱敏Gold，不引用竞品宣传形成阈值 |
| 说话人分段和实名归属 | 六家均无统一实测质量 | P0承诺“不确定可见和可纠错”，准确率阈值待测 |
| 决策和行动项提取质量 | 竞品字段证据不完整，无统一Gold | 先定义Gold和错误等级，再冻结准确率/召回率 |
| 责任人、截止时间和验收标准 | 多数竞品仅局部主张 | P0定义字段和缺失处理，不承诺AI能自动补齐所有字段 |
| 条目级证据完整率 | 市场已有回放和时间轴，完整一对一链路未确认 | 作为本产品核心功能做原型验证，覆盖率阈值TBD |
| 全链路完全离线 | 讯飞有离线/私有化方向，但全模块边界未确认 | 作为本产品架构约束；需通过网络抓包、断网和升级测试证明 |
| 远场拾音和会议规模 | MAXHUB只有公开规格，未实测 | 不把15米、20人等参数直接写入本产品首版承诺 |
| 本地加密、擦除和数据恢复 | 无本产品设计和设备验证 | 写入安全需求，具体方案和验收由安全设计阶段确定 |
| 企业愿意为差异化付费 | 无真实采购或商务证据 | 不在PRD中写确定购买结论，需访谈、试点和报价验证 |
| 价格、BOM和部署成本 | 竞品价格不可比，本产品成本未知 | 在产品定义后单独完成硬件BOM、软件成本和部署测算 |

### 能进入P0方向、但不能冻结指标的内容

- 全链路本地处理；
- 普通话转写；
- 发言人分段；
- 结构化决策和行动项；
- 会尾共同确认；
- 条目级证据；
- 正式纪要状态和版本；
- 分层删除和受控导出。

这些能力构成产品闭环，可以进入P0范围；但准确率、时延、会议人数、拾音距离、确认时长和安全认证等量化承诺必须等待真实验证。

## 15. 建议的验证顺序

| 顺序 | 验证任务 | 目标 | 主要输出 |
|---:|---|---|---|
| 1 | 真实目标企业访谈 | 验证敏感但允许录音的会议频率、现有流程和采购约束 | 需求真实性、角色、场景和付费问题清单 |
| 2 | 会尾确认低保真原型 | 验证大屏共同确认是否可接受、是否能在合理时间完成 | 流程完成率、耗时、修改点和争议处理 |
| 3 | 普通话会议Gold集 | 验证ASR、说话人、决策、待办和证据 | 指标定义、错误分类和首版阈值建议 |
| 4 | 端侧算力原型 | 验证30～120分钟会议的速度、内存、功耗和温度 | 端到端时延、资源曲线和硬件建议 |
| 5 | 断网与数据路径测试 | 证明核心链路无非授权外发 | 抓包、断网、日志、升级和异常场景结果 |
| 6 | 数据生命周期原型 | 验证音频、转写、草稿和正式纪要分别删除/保留 | 策略、审计、恢复和删除结果 |
| 7 | 受控导出试验 | 验证USB或局域网分发的权限和可用性 | 访问控制、文件标记、失败处理和审计 |
| 8 | 企业试点 | 验证持续使用、行动项闭环和采购意愿 | 多场会议使用数据、满意度和续用条件 |

在没有前四项结果前，不建议冻结最终P0性能指标或硬件规格。

## 16. 建议的首版非目标

为防止产品退化为功能堆叠，建议在后续PRD中明确以下非目标：

- 不面向完全禁止录音的会议；
- 不承诺最高涉密等级或未取得的合规认证；
- 不以云端账号和公共链接作为默认工作流；
- 不追求首版覆盖全部语言；
- 不承诺大型会议、论坛和复杂多人交叉发言；
- 不默认启用声纹或人脸实名识别；
- 不允许未经人工确认的AI结果自动正式发布；
- 不允许缺失责任人或截止时间时静默编造；
- 不把自动PPT、情绪分析、知识库问答作为首版中心能力；
- 不在P0同时接入多个企业日程、任务和文档系统；
- 不用单次样例或厂商宣传数字代表总体质量。

## 18. 给PRD的核心结论

1. **“录音＋转写＋摘要”是基础门槛，不是本产品的最终差异化。**【横向矩阵事实】
2. **首版必须完成“授权—本地处理—结构化结果—证据核对—共同确认—正式纪要—安全流转”的完整闭环。**【产品分析/合理推断】
3. **会尾共同确认、正式纪要状态和条目级证据是当前六家竞品资料中的共同证据空白，适合成为产品主轴。**【横向矩阵事实】【产品分析/合理推断】
4. **行动项必须拆分内容、责任人、截止时间、验收标准、证据、确认状态和执行状态，不能只做一段待办文本。**【产品分析/合理推断】
5. **AI默认只能生成草稿；没有可靠证据或缺少字段时必须显式标记，不得编造。**【需求假设】
