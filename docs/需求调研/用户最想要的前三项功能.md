# 端侧本地 Agent 会议纪要：用户最想要的前三项功能

- **目标产品**：集成于投影设备的端侧本地 Agent 会议纪要系统
- **目标用户**：制造、研发及工程企业的项目经理、部门负责人、会议主持人、IT 和信息安全负责人
- **生成日期**：2026-08-12

## 一、核心结论

基于目标用户的会议效率和保密需求，预计用户最想要的前三项功能为：

| 排名 | 核心功能 | 用户真正想解决的问题 | MVP 要求 |
|---|---|---|---|
| 1 | 自动生成可执行的结构化纪要 | 不想在会后花时间整理，更怕遗漏决策和任务 | 自动提取会议结论、决策、待办、责任人和截止时间，并支持会尾投屏确认 |
| 2 | 准确的离线转写与发言人识别 | 纪要需要明确谁说了什么，专业术语不能频繁出错 | 支持 3～15 人会议、发言人区分、企业人名和术语词库以及快速纠错 |
| 3 | 完全本地处理与安全流转 | 敏感会议不能上传云端，会议内容也不能被随意复制和外传 | 断网可用、本地加密、权限控制、自动删除、受控导出和操作审计 |

---

## 二、第一项：自动生成可执行的结构化纪要

### 用户需求

用户最终想要的不是一份冗长的逐字稿，而是快速知道：

- 会议讨论了什么；
- 最终决定了什么；
- 哪些问题尚未解决；
- 接下来需要做什么；
- 每项任务由谁负责；
- 任务需要在什么时候完成。

### 建议输出结构

1. 会议主题和基本信息；
2. 会议摘要；
3. 已确认的结论和决策；
4. 待解决的问题；
5. 待办事项；
6. 责任人；
7. 截止时间；
8. 下次会议安排。

### 投影设备的差异化体验

建议形成以下产品流程：

> 会议结束 → 投屏展示结论与待办 → 参会人员现场核对 → 主持人修改确认 → 本地生成正式纪要

投屏确认可以减少以下问题：

- Agent 对会议内容理解错误；
- 责任人识别错误；
- 截止时间遗漏或识别错误；
- 参会人员对结论理解不一致；
- 纪要发出后再次反复修改。

### MVP 功能范围

- 自动生成简要摘要；
- 自动提取会议结论；
- 自动提取待办事项；
- 自动识别责任人和截止时间；
- 支持主持人现场修改；
- 支持所有参会人员投屏确认；
- 确认后生成正式纪要。

---

## 三、第二项：准确的离线转写与发言人识别

### 用户需求

结构化纪要的可靠性依赖于基础转写能力。用户主要关注：

- 是否能听清不同位置的参会人员；
- 是否能区分不同发言人；
- 人名、产品名和专业术语是否准确；
- 多人交叉发言时是否会发生严重混乱；
- 识别错误后能否快速修改。

### MVP 功能范围

- 支持 3～15 人的小型固定会议室；
- 支持普通话会议离线转写；
- 支持发言人区分；
- 支持参会人员姓名预录入；
- 支持企业人名、产品名和专业术语词库；
- 支持文本与发言人的快速修改；
- 支持通过桌面麦克风或麦克风阵列提升拾音效果。

### 关键产品原则

发言人识别的价值不只是展示“谁说了什么”，更重要的是正确建立以下关联：

> 发言人 → 提议或决策 → 待办事项 → 责任人

如果暂时无法稳定识别所有发言人，产品应允许主持人在会议结束时快速补充或修正责任人，不能让错误直接进入正式纪要。

---

## 四、第三项：完全本地处理与安全流转

### 用户需求

目标用户担心的不只是音频上传云端，还包括：

- 原始录音是否会被保留；
- 转写文本保存在哪里；
- 谁能够查看或导出纪要；
- 内容删除后能否恢复；
- 设备联网后是否会自动上传数据；
- 厂商是否能够远程访问会议数据。

因此，“本地运行”需要成为一套用户可感知、可验证和可管理的安全机制，而不只是一句宣传口号。

### MVP 功能范围

- 无网络环境下完成录音、转写和纪要生成；
- 默认不向云端上传会议内容；
- 音频、转写文本和纪要均采用本地加密存储；
- 设置管理员、主持人和普通用户权限；
- 支持会议结束后立即删除原始音频；
- 支持按照企业策略自动删除历史数据；
- 支持受控 USB 或企业局域网导出；
- 记录查看、修改、导出和删除等操作；
- 提供物理麦克风静音键；
- 提供清晰、持续可见的录音状态指示；
- 会议开始前显示录音授权提示。

### 关键产品原则

建议向用户明确展示以下状态：

- 当前是否正在录音；
- 当前是否联网；
- 数据是否仅在本地处理；
- 原始音频将在什么时候删除；
- 当前纪要可以由谁查看和导出。

---

## 五、三项功能之间的关系

三项功能并非相互独立，而是一条完整的价值链：

> 准确拾音和离线转写 → 理解会议内容并生成结构化纪要 → 在本地安全保存、确认和导出

其中：

- **结构化纪要**决定用户是否感受到效率价值；
- **离线转写和发言人识别**决定纪要是否可信；
- **本地安全处理**决定目标客户是否敢用、能否采购。

任何一项明显不足，都可能导致产品价值无法成立。

## 六、首版功能优先级建议

### P0：必须具备

- 离线录音与普通话转写；
- 自动生成摘要、结论和待办；
- 提取责任人和截止时间；
- 会尾投屏确认与修改；
- 本地加密存储；
- 原始音频删除策略；
- 物理静音及录音状态提示；
- 受控导出。

### P1：重要增强

- 更准确的发言人识别；
- 企业人名和技术术语词库；
- 历史待办追踪；
- 管理员权限和操作审计；
- 企业局域网内分发纪要；
- 与会议室日程系统关联。

### P2：后续扩展

- 多语言转写和翻译；
- 实时字幕；
- 基于历史会议的本地问答；
- 自动生成汇报材料或 PPT；
- 跨会议项目进展总结；
- 更复杂的大型会议支持。

---

## 七、暂不建议作为首版重点的功能

以下功能有较强的演示效果，但不建议优先于前三项核心功能：

- 情绪分析；
- 数字人助手；
- 自动生成完整 PPT；
- 复杂知识库问答；
- 面向公开活动的实时多语言字幕；
- 大规模跨会议数据分析。

原因是这些功能不能直接解决首批目标用户最关键的三个问题：

1. 会后整理纪要耗时；
2. 决策和待办容易遗漏；
3. 敏感会议内容不能上传云端。

---

## 八、后续调研验证建议

以上功能排序属于产品假设，需要通过真实客户访谈和试用进一步验证。调研时不建议直接询问“您最想要什么功能”，而应询问用户当前的实际行为和问题。

### 建议验证的问题

- 当前每次整理会议纪要需要多长时间？
- 会议决策、责任人和截止时间的遗漏频率如何？
- 用户是否需要完整逐字稿，还是只需要结论和待办？
- 是否允许会议录音？需要什么授权流程？
- 哪些会议内容明确不能上传外部云端？
- 发言人识别错误会在多大程度上影响使用？
- 用户是否愿意在会议结束前花 1～3 分钟确认纪要？
- 哪些本地存储、删除和导出机制能够满足信息安全要求？
- 企业愿意为这些能力支付多少费用？
- 用户更希望购买新投影设备，还是为现有投影增加本地 Agent 模块？

## 九、阶段性产品判断

首版产品应围绕一个清晰的核心闭环构建：

> 本地听清会议 → 自动整理结果 → 投屏共同确认 → 安全生成并流转纪要

产品成功的关键不是生成最完整的逐字稿，而是帮助企业在不泄露敏感会议内容的前提下，更快、更准确地确认会议决策和执行任务。
