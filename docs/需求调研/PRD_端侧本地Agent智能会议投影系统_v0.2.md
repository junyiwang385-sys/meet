## 1. 产品摘要

### 1.1 候选产品定义

> **面向内容敏感、经授权可以录音的企业固定会议室，在设备端或客户控制环境内完成会议采集、理解、核验和治理，并通过会尾共享大屏共同确认决策与行动项，最终形成可追溯、可修订、可删除和可受控流转的正式纪要。**【产品暂定规则】【需求假设，待真实用户验证】

### 1.2 暂定产品形态

```text
设备端会议 Agent
  ＋ 共享显示／投影画面
  ＋ 可选麦克风阵列
  ＋ 本地加密存储与受控导出
```

本版只定义逻辑产品形态，不绑定最终投影机、一体机、外接盒子、芯片、屏幕尺寸或麦克风SKU。【产品暂定规则】

### 1.3 P0候选核心闭环

```text
明确授权
  → 本地录音与持续状态提示
  → 离线普通话转写与说话人分段
  → 提取决策、行动项、依赖和未解决问题
  → 对无证据、冲突、低置信和缺失字段显式弃权
  → 关键条目关联原话证据
  → 会尾共享大屏共同核对
  → 记录条目级责任人接受状态
  → 主持人或授权确认人独立确认正式纪要
  → 生成正式纪要版本
  → 本地保存、原始音频独立删除或受控USB导出
```

责任人接受任务与主持人确认正式纪要是两个独立动作；主持人的统一确认不得自动把所有责任人状态改为已接受。【产品暂定规则】

### 1.4 产品差异化

本产品不以“另一个转写和摘要工具”为目标，候选差异化由以下五部分共同构成：

1. **本地安全处理**：核心会议内容默认不发送外部公共云；
2. **会尾共同确认**：参会者离开会议室前共同核对关键结果；
3. **行动项闭环**：分离任务、责任团队、个人责任人、责任人接受状态、截止时间、验收标准和依赖；
4. **证据可追溯**：关键结论可回到原话、说话人和时间位置；
5. **正式纪要治理**：AI草稿只有经授权确认后才成为正式版本，并保留修订、分发、删除和审计状态。

### 1.5 P0候选成功定义与追踪原则

P0是否成立，不以“能够生成一篇摘要”判断，而以三个候选质量门共同判断：

| 质量门 | 目标 | 当前状态 |
|---|---|---|
| G1 安全与授权 | 用户知道何时录音、数据在哪里处理，并能控制停止、删除和导出 | 待真实用户、设备、安全与法律评审 |
| G2 内容可信 | 关键结果可核对，缺失字段不补造，纠正、否定、冲突和弃权关系正确 | 待真人录音Gold验证 |
| G3 正式闭环 | AI草稿可通过会尾核对和授权确认转化为受治理的正式纪要 | 待原型、权限和真实会议验证 |

P0候选需求建立以下追踪骨架：

```text
用户问题
  → P0需求ID
  → G1／G2／G3
  → 硬门／允许降级／可后移
  → 前置依赖
  → 验收场景
  → 所需证据
  → 对应决策门
```

当前暂定分类为：23项硬门、2项允许降级、1项有条件可后移。分类仅表示验证关系，不表示任何需求已经通过质量门，完整矩阵见附录C。【产品暂定规则】

三个质量门均达到后，才可以声明产品完成首版闭环。【产品分析】

## 2. 背景与问题定义

### 2.1 候选业务问题

| 问题 | 当前常见处理方式 | 候选产品机会 | 验证状态 |
|---|---|---|---|
| 会后人工整理耗时，决策和任务容易遗漏 | 主持人、秘书或项目经理手写纪要 | 自动形成结构化草稿并在会尾完成核对 | 【需求假设，待真实用户验证】 |
| 部分敏感会议不愿上传外部公共云 | 放弃会议AI，或组合本地录音和人工文档 | 在客户控制环境内完成核心闭环 | 【需求假设，待真实用户验证】 |
| 完整逐字稿不能直接推动执行 | 会后人工再次提炼任务 | 直接形成决策、行动项、依赖和未决问题候选 | 【产品分析】 |
| AI可能把建议写成决定，或补造责任人和日期 | 反复回听和人工改写 | 缺失字段显式保留，关键字段有证据并支持弃权 | 【脚本级Gold规则】【产品暂定规则】 |
| 会后异步确认产生多版本和责任争议 | 群聊、邮件或下次会议再确认 | 用共享大屏在会尾共同确认 | 【需求假设，待真实用户验证】 |
| 主持人确认容易被误解为所有责任人都已接受任务 | 人工群聊二次确认 | 分离纪要确认和责任人接受状态 | 【产品暂定规则】 |
| 关键结论无法快速回到原话 | 搜索全文或拖动时间轴 | 条目级证据直接定位原话和音频 | 【产品分析】【质量目标，待Gold验证】 |
| 音频、转写和纪要需要不同保留策略 | 在多个工具中分别管理 | 在同一治理模型中分对象保存和删除 | 【安全或生命周期要求，待评审】 |

### 2.2 核心产品问题

本产品需要验证的核心问题不是“模型能否生成摘要”，而是：

> 在敏感、允许授权录音的企业会议中，能否以用户可理解和可控制的本地方式，把会议内容转化为可信的结构化结果，并在现场形成可执行、可追溯和可治理的正式纪要？

### 2.3 价值成立的必要条件

1. **需求成立**：目标企业确实存在高频“允许录音但不愿使用外部公共云”的会议；
2. **能力成立**：端侧转写、说话人、结构化提取、证据和状态管理达到可用门槛；
3. **交互成立**：参会者愿意使用会尾大屏完成核对，且耗时可接受；
4. **治理成立**：正式纪要确认、责任人接受、遗留事项和未解决问题不会互相混淆；
5. **安全成立**：数据路径、删除、导出和权限可以被客户验证；
6. **产品载体成立**：投影或共享大屏相比电脑、手机和独立录音设备提供明显现场价值。

以上均未完成全面验证。

## 4. 产品目标与非目标

### 4.1 P0候选产品目标

1. 在无外部公共云依赖的条件下完成一次会议核心闭环；
2. 在录音前获得明确授权，并持续显示录音、静音、联网和处理状态；
3. 生成可纠错的普通话转写和基础说话人分段；
4. 结构化提取决策、行动项、责任归属、截止时间、依赖和未解决问题；
5. 对无证据、冲突、低置信、缺失、模糊、否定和纠正内容显式处理，不自动补造；
6. 为关键结论建立条目级原话证据；
7. 通过会尾投影页面完成共同核对；
8. 分离正式纪要确认和个人责任人接受任务；
9. 区分完整任务、待确认任务、遗留事项和未解决问题；
10. 只有主持人或被明确授权的确认人才能生成正式纪要；
11. 支持正式版本、修订版本、分发状态、确认工作流子状态和删除状态治理；
12. 暂定通过受控USB导出正式纪要PDF＋`manifest.json`，并保证失败不损坏本地正式版本。

以上是PRD v0.2的候选工作范围，不代表最终P0已冻结。

### 4.2 P0明确非目标

- 多语言转写、翻译和实时字幕；
- 云端备用转写作为默认链路；
- 未经人工确认自动发布正式纪要；
- 把主持人确认自动等同于所有责任人接受任务；
- 未经确认自动创建外部任务；
- 自动补全缺失责任人、团队、截止时间或依赖日期；
- 跨会议行动项持续跟踪；
- 公共云链接作为默认分享方式；
- 默认使用声纹或人脸进行实名识别；
- 通用聊天机器人、情绪分析、数字人和自动PPT；
- 超大会议、复杂远场和完美重叠发言分离承诺；
- 最终硬件SKU、BOM、价格和量产规格；
- 最高涉密等级或特定法规认证承诺；
- 将产品暂定撤回流程解释为法律意见；
- 将S／M／L原型分组解释为已验证阈值。

## 5. PRD v0.2暂定产品决策

以下决策仅用于组织本版PRD，不代表真实用户、算法、技术、安全、法务或采购验证已完成。

### 5.1 继承并更新的基础决策

| ID | v0.2暂定方向 | 对PRD的约束 |
|---|---|---|
| PD-01 | 设备端会议Agent＋共享显示＋可选麦克风阵列 | 不绑定最终硬件SKU |
| PD-03 | 默认不使用外部公共云；客户局域网需单独授权和说明 | 本地与客户控制环境必须可解释 |
| PD-04 | 核心对象是经确认的决策、行动项和正式纪要 | 逐字稿主要作为证据和纠错基础 |
| PD-05 | 主持人或被明确授权的确认人生成正式纪要；责任人接受任务为独立条目级状态 | 普通编辑、主持人确认和个人接受不得混为一体 |
| PD-06 | 缺失或冲突任务先待确认；正式化前转为完整任务、遗留事项、未解决问题或删除误提取 | 不阻止其他完整且已核验内容正式确认 |
| PD-07 | P0只处理单次会议提取、接受状态和确认 | 跨会议执行跟踪放入P1；接受不等于完成 |

## 8. 端到端用户流程与状态

### 8.1 主流程

| 阶段 | 用户动作 | 系统候选行为 | 完成条件 |
|---|---|---|---|
| 会前配置 | 选择会议、主持人、参会人、保密等级和数据策略 | 显示处理位置、联网状态、存储、麦克风和授权信息 | 授权完成，设备可开始录音 |
| 会中记录 | 开始、暂停、物理静音、继续或停止录音；可提出撤回 | 本地录音、转写、说话人分段、结构化草稿和证据缓存；状态持续可见 | 主持人停止录音，或撤回触发停止后续采集 |
| 会尾准备 | 等待或进入草稿确认 | 聚合决策、任务候选、依赖、未决问题、弃权状态和缺失字段 | 草稿达到可展示状态 |
| 会尾核对 | 查看、编辑、删除、合并、补字段、分流对象和查看证据 | 保留人工修改差异，不用模型自动补造字段 | 所有拟进入正式版本的条目均已核对或处理 |
| 责任状态核对 | 责任人表达接受／拒绝，或保持待接受 | 独立记录`owner_confirmation_status`和证据 | 条目责任状态明确；不要求全部为`confirmed` |
| 正式生成 | 授权确认人确认内容、分发范围和音频处理选择 | 生成正式版本、确认记录、审计事件和数据对象状态 | 正式版本完整写入 |
| 延后处理 | 选择稍后确认、重新进入、放弃或删除草稿 | 保持非正式状态和工作流子状态 | 按权限继续处理或结束 |
| 会后管理 | 查看、修订、导出或删除 | 保留版本链，执行权限和生命周期策略 | 按企业策略持续管理 |

### 8.2 录音与撤回状态模型

```text
未授权
  → 已授权／待录音
    → 录音中
      ↔ 已静音／已暂停
      → 已停止
        → 本地处理中
          → 草稿可确认

录音中
  → 收到撤回／停止采集请求
    → 立即停止后续采集或进入物理静音
      → 撤回请求处理中
```

保护条件：

- 未授权不得进入录音中；
- 物理静音时不得继续采集有效麦克风音频；
- 录音、静音、暂停、停止和处理状态必须持续可见；
- 收到有效撤回请求后不得自动恢复录音，再次开始需要重新授权；
- 停止后续采集不自动等于删除此前数据；删除和正式记录异议分别处理；
- 断开公网不应导致核心流程退出，但实际能力需设备验证；
- 麦克风异常或存储不足不得伪装成正常录音。

撤回规则仅为产品工作流骨架，具体授权主体、法域、审批和保留义务待法务与安全确认。【法律规则，待专业确认】

### 8.3 内容状态模型

```text
AI草稿
  → 待确认
    → 正式纪要
      → 修订草稿
        → 待确认
          → 已修订（新正式版本）
```

内容状态可按权限和策略进入“已删除”。分发状态、确认工作流子状态和对象删除状态均与内容状态独立管理。

### 8.4 待确认工作流子状态

| 子状态 | 定义 | 是否正式 | 允许的主要操作 |
|---|---|:---:|---|
| `active` | 正在现场或本地核对 | 否 | 编辑、分流、看证据、确认或延后 |
| `deferred` | 已选择稍后确认 | 否 | 授权人员重新进入、放弃或发起删除 |
| `overdue` | 超过企业配置的候选期限但仍未确认 | 否 | 重新进入、放弃或按策略处理；不得自动正式化 |
| `abandoned` | 授权人员明确放弃正式化 | 否 | 按权限重新激活或单独删除；不得导出为正式纪要 |

- 没有企业策略时不设置强制自动超时；
- 超时不得自动正式化或自动删除；
- 放弃正式化不等于数据已删除；
- 稍后确认记录操作者、时间、原因和可选`confirmation_due_at`。【产品暂定规则】

### 8.5 执行相关对象状态

| 类型 | 定义 | 是否属于正式行动项 | 正式纪要位置 |
|---|---|:---:|---|
| 完整任务 | 动作、个人责任人、截止时间和证据满足正式化条件 | 是 | 已确认行动项；责任人接受状态单独展示 |
| 待确认任务 | 动作明确，但关键字段、证据或语义缺失／冲突／低置信 | 否 | 仅在草稿或待确认工作区 |
| 遗留事项 | 会议确认需要后续处理，但当前不足以成为完整任务 | 否 | 正式纪要独立“遗留事项”章节 |
| 未解决问题 | 尚未形成决定或行动承诺的问题、争议或政策 | 否 | 正式纪要独立“未解决问题”章节 |

待确认任务在正式化前必须补齐、转遗留事项、转未解决问题或删除为误提取。遗留事项和未解决问题后续转为行动项或决策时，需要通过修订版本完成。【产品暂定规则】

### 8.6 分发状态模型

```text
未分发 → 分发中 → 已分发
              ↘ 分发失败
已分发 → 已撤回（如后续能力支持）
```

P0暂定支持受控USB导出，不承诺可撤回已经复制到外部介质的文件；该边界必须在导出前明确提示。【安全或生命周期要求，待评审】

### 8.7 数据对象删除状态

```text
活动中 → 待删除 → 已删除 → 删除已验证
                    ↘ 删除失败／需处理
```

音频、转写、AI草稿、正式纪要、证据索引、撤回／删除请求和审计记录分别维护状态，不得用一个“会议已删除”状态掩盖实际删除范围。

### 10.3 责任归属、任务接受与纪要确认

候选字段：

- `responsible_team`：明确承担责任的组织、部门、项目组或职能团队；
- `individual_owner`：经明确指派、自我承诺或人工确认的具体人员；
- `ownership_status`：责任归属完整程度；
- `ownership_evidence`：支持团队或个人归属的原话或人工确认记录；
- `owner_confirmation_status`：具体责任人是否明确接受任务；
- `owner_confirmation_evidence`：口头接受、受控界面操作或授权人员人工记录；
- `minutes_confirmation_status`：该条目是否被纳入授权确认的正式纪要。

责任归属状态：

| 责任团队 | 个人责任人 | `ownership_status` | 展示方式 |
|---|---|---|---|
| 缺失 | 缺失 | `unassigned` | 责任团队待指定；个人责任人待指定 |
| 已明确 | 缺失 | `team_assigned_person_pending` | 已明确责任团队；个人责任人待指定 |
| 缺失 | 已明确 | `person_assigned` | 显示具体责任人；团队可待补充 |
| 已明确 | 已明确 | `person_assigned`或`confirmed` | 同时显示团队和个人 |

个人接受状态：

| 状态 | 暂定语义 | 正式纪要处理 |
|---|---|---|
| `not_required` | 当前没有个人责任人，没有可执行的个人接受动作 | 不能展示为个人责任完整；转待确认或遗留事项 |
| `pending` | 已指定个人，但尚无明确接受证据 | 可显示“已指派、待接受”，不得显示“已接受执行” |
| `confirmed` | 个人明确接受，且存在口头、界面或人工确认记录 | 可显示“责任人已接受” |
| `rejected` | 被指定人员明确拒绝或否认责任 | 转责任争议、待重新指定、遗留事项或未解决问题 |

关键规则：

1. 主持人确认正式纪要不得自动把`owner_confirmation_status`设为`confirmed`；
2. 已明确团队但没有具体人员时，不得标记为完全无责任归属；
3. 不得因为某人属于责任团队或提出任务就自动指定该人员；
4. 不得从相邻任务借用团队、责任人或日期；
5. 团队责任、个人责任和个人接受分别关联证据；
6. P0不冻结可信个人身份实现，匿名点击不得自动视为本人数字确认。

## 11. 语义提取、对象分流与证据规则

### 11.1 决策规则

- 只有明确达成并具有约束含义的结论进入决策候选；
- 建议、偏好、普通讨论、技术权衡和被否定方案不生成正式决策；
- 同一决策的补充确认不重复生成新决策；
- 会议语义上明确的决策仍先进入AI草稿，产品内确认后才成为正式纪要；
- 决策存在冲突或证据不足时进入弃权／未解决问题，不由模型裁决。

### 11.2 行动项与对象分流规则

- 至少存在明确动作，才可进入行动项候选；
- 责任团队、个人责任人或截止时间允许缺失，但必须醒目标记；
- 发言人不等于任务责任人，提出者不等于任务责任人；
- 同一任务在多个说话人、多个片段间补充时，不应被拆成多个任务；
- 验收标准、依赖和执行状态没有明确证据时保持缺失；
- 待确认任务在正式化前必须补齐、转遗留事项、转未解决问题或删除误提取；
- 遗留事项和未解决问题不得计入完整行动项数量；
- 主持人确认纪要不自动代表责任人接受任务；
- 责任人拒绝后，条目不得继续展示为已接受的完整任务。

### 11.3 依赖、遗留事项与未解决问题规则

- 依赖项与行动项独立建模并建立关联；
- 依赖未到位不等于任务取消；
- 自动依赖／未解决问题识别允许降级为人工分流，但降级必须可见；
- 遗留事项表示“确认需要后续处理但当前不完整”；
- 未解决问题表示“尚未形成决定或行动承诺”；
- “需要与某部门确认”不自动产生具体责任人或期限；
- 争议内容不由AI裁决，可关联多个证据片段；
- 遗留事项和未解决问题后续转为行动项或决策时，必须生成修订版本。

### 11.4 证据关联要求

每项正式决策和完整行动项至少具有：

```text
条目ID与版本
  ＋ 一个或多个证据片段ID
  ＋ 原始发言人或候选说话人
  ＋ 开始和结束时间
  ＋ 原始转写
  ＋ 音频定位（音频存在时）
  ＋ 支持／缺失／冲突／低置信／人工解决状态
  ＋ 人工修改和最终确认记录
```

关键规则：

- 时间纠正需要同时关联旧值、纠正发言和最终确认发言；
- 人工补充的责任人或接受状态必须标记为人工证据，不能伪造成语音证据；
- 没有可靠证据时不得生成看似完整的引用；
- 修改结构化内容不能覆盖原始AI输出和原证据关系；
- 只有全文时间轴入口不算条目级证据闭环；
- 转写、说话人或时间边界修改后的证据重算和失效规则仍待算法与客户端评审。

### 11.5 产品级弃权协议

产品采用“宁可显式缺失，不用无证据猜测”的暂定规则，不设置未经Gold校准的数值阈值：

| 触发条件 | `extraction_status` | 产品处理 | 是否可直接正式化 |
|---|---|---|:---:|
| 证据明确且一致 | `supported` | 展示候选值和证据，等待人工核对 | 可以，经授权确认后 |
| 找不到支持证据 | `evidence_missing` | 字段留空或条目标为待核验，不生成虚假引用 | 否 |
| 多组证据相互冲突 | `conflict` | 保留冲突证据，转待确认或未解决问题 | 否 |
| 模型或规则低置信 | `low_confidence` | 显示语义状态，不默认展示为确定事实 | 否 |
| 动作明确但关键字段缺失 | `field_missing` | 保留动作，缺失字段为空，进入待确认任务 | 否，除非转遗留事项 |
| 人工基于证据解决 | `human_resolved` | 记录修改人、时间、前后值和来源 | 可以，经正式确认后 |

补充规则：

1. 默认不在共享大屏显示难以解释的模型概率；
2. 同一条目存在多种风险时按更保守状态处理；
3. 高风险候选进入“待核验候选”，不得静默隐藏或升级；
4. 人工补充值必须标记为人工证据；
5. schema通过不得自动把弃权状态升级为已确认；
6. 具体触发阈值、校准方法和误差容忍待音频级Gold与算法评审。【产品暂定规则】【质量目标，待Gold验证】

### 11.6 原始数据删除后的证据降级

| 源数据状态 | 条目证据状态 |
|---|---|
| 音频和转写均存在 | 原文＋音频可核验 |
| 音频已删除、转写保留 | 仅转写可核验 |
| 音频和转写均删除 | 原始证据已按策略删除；正式纪要可按策略保留 |

删除后不得继续显示无效播放入口。是否保留哈希、摘要指纹或删除证明不在本版冻结。

## 12. 会尾投影确认体验

### 12.1 进入条件

- 录音已经停止，或主持人明确进入会尾确认；
- AI草稿已达到可展示状态；
- 当前内容状态明确显示为“AI草稿”或“待确认”；
- 主持人或授权确认人在场；
- 敏感内容展示范围符合会议权限；
- 系统可以显示无证据、冲突、低置信和缺失字段状态。

### 12.2 默认信息优先级与原型分组

```text
顶部：会议名称｜录音已停止｜本地处理状态｜联网状态｜数据外发状态｜保密等级

高风险区：冲突｜无证据｜低置信｜字段缺失｜未核对
决策区：候选决策｜核对状态｜证据入口
行动项区：任务｜责任团队｜个人责任人｜接受状态｜截止时间｜依赖
遗留区：遗留事项｜未解决问题｜风险｜争议

底部：已核对数量｜未核对数量｜稍后确认｜放弃确认｜确认并生成正式纪要
```

完整逐字稿不默认铺满主界面，按权限和需要展开。【产品暂定规则】【需求假设，待真实用户验证】

以下数量仅作为原型分组，不是已验证阈值：

| 候选规模 | 关键条目数 | 候选交互 |
|---|---:|---|
| S | 1～8项 | 单一核对流程，可在主界面依次检查 |
| M | 9～20项 | 按对象分区，显示核对进度和待处理数量 |
| L | 21项以上 | 高风险优先、分阶段核对；未核对内容继续保持待确认 |

### 12.3 输入设备候选规则

| 输入方式 | P0候选能力 |
|---|---|
| 触控屏 | 直接选择、展开、状态切换和短文本修改 |
| 鼠标／键盘 | 完整导航、文本编辑和快捷核对 |
| 遥控器／方向键 | 导航、展开、状态选择和确认；不承担长文本录入 |
| 受控主持人终端 | 候选补充方式；必须在客户控制环境内，并重新评估身份和数据路径 |

如果当前输入设备无法完成必要文本修改，应允许连接受控键鼠或选择稍后确认，不得迫使主持人使用遥控器输入长文本。最终硬件是否触控、是否提供主持人终端继续保持未冻结。

### 12.4 候选确认步骤

1. 先处理冲突、无证据、低置信和缺失字段；
2. 核对候选决策，删除或降级普通讨论和错误决策；
3. 核对行动项、责任团队、个人责任人、截止时间、验收标准和依赖；
4. 将不完整候选补齐、转遗留事项、转未解决问题或删除误提取；
5. 责任人表达接受、拒绝或保持待接受；
6. 点击条目查看相关原话和证据；
7. 时间纠正只展示最终有效值，并允许查看旧值和纠正证据；
8. 无法解决的争议转为未解决问题；
9. 每个拟进入正式版本的条目设为已核对／已处理；
10. 选择分发范围和音频处理方式；
11. 由授权确认人生成正式纪要，且不自动更改个人接受状态。

### 12.5 正式确认完成条件

- 正式决策具有明确语义和证据；
- 完整任务具有个人责任人、截止时间和证据；
- 个人责任人接受状态明确展示，允许`pending`但不得冒充`confirmed`；
- `rejected`或无个人责任人的事项已转为遗留事项或未解决问题；
- 待确认任务已被补齐、分流或删除误提取；
- 遗留事项和未解决问题没有被计入完整行动项；
- 无证据、冲突和低置信内容没有被直接正式化；
- 所有拟进入正式版本的条目均已核对／处理；
- 确认人、确认时间和版本可完整记录；
- 分发范围和音频处理选择已明确。

### 12.6 体验目标边界

- “会尾1～3分钟完成确认”只作为S规模原型的候选目标，需真实用户测试；
- M和L规模单独统计，不共享同一时长承诺；
- S／M／L数量可由原型结果调整，不属于已验证阈值；
- “一次主要操作进入证据”仅为候选目标，需原型验证；
- 草稿处理未完成时允许稍后确认，但不得生成正式纪要；
- 超时不得自动正式化或自动删除；
- 放弃确认不等于删除数据；
- 未核对条目不得静默随正式版本发布。

## 13. 本地、安全、撤回与数据生命周期要求

### 13.1 “本地／客户控制环境”候选定义

- 会议音频、转写、说话人结果、结构化结果和证据默认不发送外部公共云；
- 核心闭环在断开公网时仍可运行；
- 客户局域网服务器如被采用，必须明确其属于客户控制环境并单独授权；
- 软件升级、模型升级、许可、遥测和故障日志不得隐含传输会议正文或音频；
- 所有外发路径必须有清单、策略、用户可见状态和审计；
- “设备联网”和“会议数据是否外发”必须分别展示。

以上边界需产品、安全、法务和目标客户共同确认。

### 13.2 候选数据流

```text
麦克风／音频输入
  → 本地临时缓冲
  → 本地ASR
  → 本地说话人分段
  → 本地结构化提取与弃权分流
  → 本地证据索引
  → AI草稿
  → 会尾核对与责任接受状态记录
  → 授权确认
  → 本地正式纪要
  → 受控USB逻辑导出包（PDF＋manifest.json）
```

任何实际实现若偏离该路径，必须重新评估产品定位和安全声明。

### 13.3 分对象存储与生命周期

| 数据对象 | P0候选要求 | 未决事项 |
|---|---|---|
| 原始音频 | 本地加密存储；可在确认后独立立即删除或按策略保留 | 加密算法与密钥实现、默认期限、擦除等级、缓存和备份副本 |
| 转写文本 | 本地加密存储；与音频分开治理并支撑证据核验 | 保存期限、脱敏和音频删除后的策略 |
| AI草稿／待确认内容 | 本地加密存储；记录`active/deferred/overdue/abandoned`，不作为正式依据 | 默认期限、提醒和自动策略 |
| 正式纪要 | 本地加密存储；按权限查看、修订、删除和导出 | 企业期限、法律保留和备份策略 |
| 证据索引 | 本地加密存储；与源数据联动，源数据删除后状态降级 | 是否保留指纹或删除证明 |
| 撤回／删除请求 | 记录请求范围、状态、处理人和结果 | 申请主体、审批、法域和客户制度 |
| 审计记录 | 本地加密存储并记录关键操作，正文最小化 | 保存期限、访问角色和不可篡改要求 |

放弃确认不等于删除草稿；草稿删除必须作为独立对象操作执行并审计。【产品暂定规则】

### 13.4 加密和密钥要求边界

本版只定义以下安全目标，不选择算法、芯片或密钥实现：

- 静态会议数据必须采用本地加密存储；
- 密钥不得与会议数据以同等风险方式存放；
- 管理、确认、审计和维护权限应分离；
- 设备丢失、磁盘拆卸、维修和恢复出厂场景不得轻易暴露会议内容；
- 厂商维护人员默认不得读取客户会议内容和密钥；
- USB文件是否加密、水印、设有效期或绑定接收者，需后续威胁建模与客户验证。

### 13.5 受控USB导出要求

P0暂定逻辑默认包：

```text
<安全文件名目录>/
  ├── formal_minutes.pdf
  └── manifest.json
```

产品规则：

- 默认只导出正式纪要PDF和机器可读`manifest.json`；
- 默认不包含原始音频、完整逐字稿、AI草稿、待确认内容、原始证据片段、审计日志全文和诊断信息；
- PDF可显示证据在源设备上的可用状态，但默认不复制敏感原话和音频；
- 原始音频是否允许导出继续作为U-001未决问题；
- P0默认不导出可编辑DOCX，真实客户强需求可在正式评审中调整；
- 导出前显示对象、版本、保密等级、接收范围和包含内容；
- 未授权导出必须阻止并记录；
- 成功、失败和阻止均形成审计事件；
- 导出失败不得损坏本地正式版本；
- 文件名是否脱敏、PDF/A、加密容器、数字签名、文件摘要、水印、有效期、白名单和接收者绑定均未冻结；
- USB外部二次复制和撤回能力无法保证时，必须明确提示。

PDF＋`manifest.json`是产品暂定逻辑格式，不表示IT／安全或客户已经批准该导出方案。【产品暂定规则】【安全或生命周期要求，待评审】

### 13.6 撤回授权后的产品工作流

撤回授权拆分为三个动作：

| 请求类型 | 暂定产品行为 | 专业边界 |
|---|---|---|
| 停止后续采集 | 立即停止录音或进入物理静音，并记录请求时间和结果 | 不自动决定此前数据是否删除 |
| 限制使用／发起删除请求 | 创建对象级请求，列出音频、转写、草稿、证据和正式纪要范围 | 删除权限、审批和保留义务待法务／安全确认 |
| 对正式记录提出异议 | 不无痕修改或删除正式版本；进入修订、限制访问或争议处理流程 | 法律和业务处理待专业确认 |

补充规则：

- 撤回后不得自动恢复录音，再次开始需要重新授权；
- 请求至少记录请求人／代办人、时间、范围、状态、处理人和结果；
- 正式纪要生成前，如策略允许删除，应按对象执行并更新证据状态；
- 已生成正式纪要时，不得通过删除音频无痕改变正式内容；
- 遇到企业强制保留、法律留置、审计义务或其他参与者权益时，只显示“请求处理中”，不得由产品自行判断法律优先级；
- 删除失败必须显示失败对象和待处理状态。

本节仅为产品暂定工作流，不构成法律意见。【法律规则，待专业确认】

## 14. 主要异常流程

| 异常 | P0候选处理 |
|---|---|
| 参会者不同意录音 | 不开始录音，或按企业和法律规则退出录音流程 |
| 会议中撤回授权 | 立即停止后续采集；删除请求和正式记录异议分别建单处理，不自动作法律判断 |
| 麦克风无信号或被静音 | 持续提示，不得假装正常录音 |
| 断开公网 | 核心流程继续；显示断网和数据路径状态 |
| 存储空间不足 | 会前预警；必要时阻止开始；不得静默丢失音频 |
| 转写或结构化处理积压 | 显示进度；允许稍后确认；不得生成伪完整结果 |
| 说话人不确定 | 使用未知或候选标签，允许会尾修正 |
| 无证据、冲突或低置信 | 显式弃权并进入待核验，不输出确定值或虚假引用 |
| 责任团队、个人责任人或截止时间缺失 | 醒目标记，不补造；允许补充或转遗留事项 |
| 责任人待接受 | 可在正式纪要中显示“已指派、待接受”，不得显示为已接受 |
| 责任人拒绝 | 转责任争议、待重新指定、遗留事项或未解决问题 |
| 时间被后续发言纠正 | 当前值更新为最终有效值；旧值保留在证据和修改记录 |
| 决策存在争议 | 转为未解决问题并保留相关证据，不由AI裁决 |
| 确认人不在场 | 进入`deferred`，保持待确认，不发布正式纪要 |
| 超过候选确认期限 | 进入`overdue`，不得自动正式化或删除 |
| 授权人员放弃确认 | 进入`abandoned`；不导出为正式纪要，删除另行处理 |
| 确认过程中断电 | 恢复最近安全状态；正式版本不得部分写入 |
| 音频在确认前被要求删除 | 提示证据影响；按权限和规则处理请求并更新证据状态 |
| 未授权导出 | 阻止并记录安全事件 |
| USB导出失败 | 保留本地正式版本，提示原因并允许安全重试 |
| 删除失败或仍存在副本 | 显示“删除失败／需处理”，不得宣称已彻底删除 |
| 设备时间异常 | 阻止或提示确认时间可靠性问题，避免生成错误审计时间 |

## 19. 关键风险与缓解方向

| 风险 | 可能影响 | 当前缓解方向 |
|---|---|---|
| 真实需求强度不足 | 产品差异化无法转化为采购价值 | 优先访谈敏感会议高频角色，不以内部推断替代证据 |

| 待确认状态过多 | 主持人遗漏延后或遗留事项 | 高风险优先、进度提示、工作流子状态和明确责任 |
| 转写或说话人质量不足 | 后续结构化结果和证据不可信 | 建立真人音频Gold，保留未知标签和快速纠错 |
| 结构化模型补造字段 | 错误任务进入正式纪要 | 强制弃权状态、缺失字段空值、证据门和人工确认 |
| 弃权候选过多 | 会尾页面噪声增加 | Gold校准、排序、折叠和分规模验证，不提前写数值阈值 |
| 本地算力不足 | 长会议处理积压、等待过长 | 30／60／120分钟压测后再冻结模型和硬件 |
| “本地”数据路径不可证明 | 安全定位失信 | 数据流图、抓包、接口清单和遥测审查 |
| USB逻辑格式被误认为安全方案已定 | 评审或客户误解 | 明确PDF＋manifest仅为对象格式，安全容器和介质策略TBD |
| USB成为外泄路径 | 无法通过信息安全评审 | 默认最小导出对象、权限、提示、审计和安全方案验证 |
| 撤回流程被误写成法律结论 | 合规风险 | 持续标注产品骨架，正式法务意见优先 |
| 删除无法覆盖缓存和副本 | 错误宣称数据已彻底删除 | 分对象盘点、删除状态和失败可见性 |
| 管理员权限过大 | 会议正文被无关运维人员访问 | 设备管理权与内容访问权分离 |
| 产品形态过早绑定 | 限制部署方式并增加BOM风险 | v0.2仍只定义逻辑形态，不冻结SKU |
| 范围持续扩大 | P0无法形成闭环 | 坚持单会、普通话、本地、确认和治理主线 |

## 20. 后续版本边界

### 20.1 P1前移条件

仅在验证出现以下证据时考虑把P1能力前移：

- 实时字幕；

- 情绪和注意力分析；
