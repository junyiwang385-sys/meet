# 断点续跑 / 崩溃恢复机制（resume & crash-safety）

> 面试官问:"会议处理到一半,LLM 阶段崩了或断电,能断点继续吗?"
> 一句话:**能——三级 checkpoint(阶段/LLM 请求/ASR 块)+ 原子写崩溃安全,最坏只丢崩溃那一刻正在生成的单条 LLM 请求。**
> 本文既是系统设计说明,也是面试话术。以代码为准,2026-09-14。

---

## 一、三级断点续跑

### ① 阶段级（harness）
- `stage_status.json` 记录每个阶段状态(分离 / ASR / 转写 / 摘要 / enrichment …),终态 = `{succeeded, reused, skipped}`。
- 重启(`resume=True`,板端默认)时 `resolve_first_unfinished_stage()` **找到第一个未完成阶段,从那接着跑**,已完成阶段整个跳过。
- 代码:`src/meeting_agent/adapters/board/board_harness_worker_v0.py`(`TERMINAL_STAGE_STATUSES`、`resolve_first_unfinished_stage`、`stage_status.json`)。

### ② LLM 请求级（面试官真正问的这层）
每个 LLM 调用(**每个块摘要、概览、每批发言人、行动项复核**)有独立 `request_dir`,落 5 个产物:

| 产物 | 作用 |
|---|---|
| `final_json.txt` | LLM 原始输出 |
| `validated_result.json` | 校验后的结构化结果 |
| `validation.json` | 质量门结果(pass/fail) |
| `status.json` | finish_reason / context_truncated |
| `request_identity.json` | fingerprint + 各产物 sha256 |

**重启复用判定** `_load_reusable_request()`——**六重全过才复用,否则重跑该请求**:
1. 5 个产物文件都在;
2. `fingerprint` 匹配(**输入/参数没变**;块内容或配置一变,指纹变 → 绝不复用旧的);
3. **每个产物 sha256 都对**(文件没损坏);
4. `status.finish_reason == "stop"` 且未截断(**这次请求是干净跑完的,不是崩一半**);
5. `validation.status == "pass"`;
6. **拿缓存输出重跑一遍校验器,结果必须完全一致**(防校验逻辑变更后盲信旧结果)。

→ **崩一半的块没有完整产物 → 判不可复用 → 重跑;跑完的块秒跳过。** 粒度 = 单个 LLM 请求。
- 代码:`src/meeting_agent/stages/product_summary.py`(`_load_reusable_request` / `_save_reusable_request` / `reused_request_count`;`ProductSummaryConfig.resume`)。

### ③ ASR 级
按音频块缓存,`done_ids` 跳过已转写块("all chunks are already cached")。
- 代码:`src/meeting_agent/adapters/board/asr/meeting_spk_asr_batch_v1.py`(`--resume` 默认 True)。

## 二、地基:checkpoint 的崩溃安全 = 原子写

`atomic_write_json / atomic_write_text`(`src/meeting_agent/storage/artifacts.py`):
```python
写 path.tmp  →  os.fsync(强制落盘)  →  os.replace(tmp, path)   # 同盘原子改名
```
- **断电/崩溃发生在写 checkpoint 的中途,也永远不会留下"写一半的坏文件"**:磁盘上要么是旧的完整版、要么是新的完整版,`.tmp` 残片被忽略。
- **为什么关键**:没有原子写,断电正好写到 checkpoint,会把"续跑所依赖的文件"本身写坏 → 续跑直接崩。**原子写是整个断点续跑能成立的前提。**

---

## 三、诚实边界（好答案要主动说限制）

1. **单次 LLM 调用生成到一半崩**:那条请求的输出没落盘(或 `status≠stop`)→ **整条请求从头重跑**,**不能"续 token"**。这是 LLM 调用固有的——重做请求,不是重做 token。
2. **配置/输入变了**:`verify_resume_snapshot` **主动拒绝复用并报 mismatch**(不静默混新旧)——安全,但意味着改参数 = checkpoint 作废。
3. **坏 checkpoint 能自愈**:sha256 + 重校验会识别损坏/被篡改的产物并重跑,不盲信。
4. **评测 vs 生产**:评测入口 `eval/pc_full_minutes.py` 用 `resume=False`(每次全新跑,评测要干净);**生产板端 harness 默认 `resume=True`**,续跑常开。

## 四、面试话术（结构化答法）

> "**能,做了三级断点续跑**:阶段级看 `stage_status.json` 从第一个未完成阶段续;**LLM 请求级**每个块的输出 + 校验结果落盘,重启时靠**指纹匹配 + sha256 + 重跑校验**三重判定决定复用还是重跑;ASR 按音频块缓存。**checkpoint 用原子写(tmp→fsync→rename),保证断电写一半也不会损坏续跑依赖的文件**。最坏情况只丢崩溃那一刻正在生成的单条请求——因为一次 LLM 生成没法从半截 token 续,只能整条重做;这是我刻意接受的粒度。"

覆盖面试官想听的四点:**幂等复用 / 崩溃一致性(原子写)/ 防串防坏(指纹+哈希+重校验)/ 诚实的粒度极限**——比"能/不能"高一层。
