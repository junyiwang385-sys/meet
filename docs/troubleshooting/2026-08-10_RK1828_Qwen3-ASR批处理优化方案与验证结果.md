# RK1828 Qwen3-ASR 批处理优化方案与验证结果

> 日期：2026-08-10  
> 范围：保持现有 bridge4 切片与识别参数不变，将 Qwen3-ASR 从逐 chunk 重复加载改为单进程批量推理。

## 一、优化背景与目标

原方案已经完成说话人分离、ASR 切片和全量转写，但 Python 每处理一个 chunk 都会重新启动一次 C++ demo：

```text
87 ×（启动进程 → 加载 encoder/LLM/tokenizer → 识别 1 个 chunk → 释放模型）
```

全量 87 个 chunk 的 runner 累计耗时为 `587.771s`。本次优化目标是：

| 目标 | 要求 |
|---|---|
| 减少模型加载 | 整场会议只加载一次 Qwen3-ASR |
| 保持识别质量 | 音频、切片、模型参数和解码参数不变 |
| 保持资源安全 | chunk 串行推理，不并行抢占 NPU |
| 防止状态污染 | 每个 chunk 前清除 KV cache 并重置回调状态 |
| 支持恢复 | 每条结果即时写入 JSONL，可断点续跑 |
| 可回滚 | 使用旁路源码、二进制、脚本和输出目录，不覆盖稳定链路 |

---

## 二、未改变的 ASR 合并方案

本次只优化模型运行方式，没有改变 speaker diarization 和 bridge4 切片逻辑：

```text
184 个后处理 speaker segment
  → bridge4 合并为 31 个 ASR unit
  → 按约 30s 切为 87 个 ASR chunk
  → Qwen3-ASR 转写
  → 同 speaker 文本合并为 meeting transcript
```

当前切片参数：

| 参数 | 值 | 作用 |
|---|---:|---|
| CAM++ window | `3.0s` | 说话人特征窗口 |
| 聚类阈值 | `0.68` | speaker cosine clustering |
| `merge_gap_sec` | `3.2s` | 合并相邻同 speaker 片段 |
| `bridge_fragment_sec` | `4.0s` | 跨越短 `unknown_fragment` |
| `max_asr_sec` | `30s` | ASR chunk 目标长度 |
| `min_target_asr_sec` | `8s` | 避免生成很短的尾部 chunk |
| `pad_sec` | `0.3s` | 实际切音频时前后补音 |
| `turn_merge_gap` | `1.0s` | ASR 后合并同 speaker 文本 |

`unknown_boundary` 仍单独保留，不跨不同主说话人合并。

## 三、优化实现

### 1. 运行方式变化

| 原 One-shot 方案 | 新 Batch 方案 |
|---|---|
| 每个 chunk 启动一次 C++ demo | 一场会议只启动一次 C++ runner |
| 模型加载 87 次 | 模型加载 1 次 |
| 每次完成后释放全部模型 | 87 条完成后统一释放模型 |
| Python 循环执行 87 次 `subprocess.run()` | Python 生成 manifest 后只调用 runner 1 次 |
| 从 stdout 的 `text res:` 解析文本 | runner 每条直接写结构化 JSONL |

新流程：

```text
Python 生成 87 个 WAV 和 manifest.tsv
  → 启动 rknn_qwen3_asr_batch_demo
  → 加载 tokenizer、embedding、encoder、内部 LLM 一次
  → 串行处理 87 个 chunk
       清 KV cache
       重置 callback/perf 状态
       读取 WAV 并推理
       写入一行 JSONL 并 fflush
       释放该 chunk 临时内存
  → 统一释放模型和 NPU
  → Python 合并 speaker + text
```

### 2. 每个 chunk 的状态管理

| 批次内复用 | 每条音频前后重置/释放 |
|---|---|
| RKNN encoder/LLM context | `rknn3_session_clear_kvcache(..., RKNN3_KVCACHE_CLEAR_ALL)` |
| 模型权重和共享 internal memory | 当前转写字符串、语言标记、首 token 时间 |
| tokenizer 和 embedding mmap | `rknn_perf_metrics_t` |
| prefix/postfix embeddings | 输入音频、audio embeddings、临时拼接 embedding |

显式清理 KV cache 后，正序 `A→B` 与逆序 `B→A` 的识别结果完全一致，证明没有跨 chunk 上下文污染。

### 3. Manifest 与结果协议

Batch runner 输入为 TSV：

```text
job_id<TAB>absolute_wav_path
```

每条完成后立即追加一行 JSONL，主要字段包括：

```json
{
  "job_id": "1",
  "wav_path": "/userdata/.../chunk_0001.wav",
  "status": "ok",
  "text": "转写文本",
  "audio_duration_sec": 30.6,
  "elapsed_sec": 0.81,
  "audio_latency_ms": 0,
  "llm_elapsed_ms": 0,
  "prefill_tokens": 0,
  "decode_tokens": 0
}
```

Python 驱动根据 JSONL 中最新的成功记录生成 pending-only manifest；异常中断后重新运行时，只处理未成功的 chunk。

| 检查项 | 结果 |
|---|---|

| 测试后 LLM 退出 | `LLM_PROCESS_EXITED` |

验证了以下资源顺序可正常工作：


## 八、回滚方式

Batch 方案没有覆盖稳定文件，发生异常时直接切回：

```text
meeting_spk_asr_v1.py
  → rknn_qwen3_asr_demo
  → /userdata/meeting_agent/output/asr_spk_v2_bridge4_full
```

不需要恢复模型或重新编译。Batch 源码、runtime、Python 驱动和结果目录均可独立停用或删除，不影响原链路。

## 九、最终结论

```text
本次优化在不改变 bridge4 切片、speaker 标签、时间戳、模型和解码参数的前提下，将 Qwen3-ASR 从“每个 chunk 重复加载模型”改为“整场会议加载一次、串行处理全部 chunk”。

全量 87 个 chunk 的结果与原 One-shot 方案逐字一致，Runner 耗时由 587.771s 降至 65.966s，实现 8.91× 加速并节省 88.8% 时间。断点续跑、KV cache 隔离、单条即时落盘以及 ASR→Qwen3-4B 的 NPU 资源切换均验证通过。

该 Batch Runner 可作为后续离线会议编排器中的正式 ASR worker；原 One-shot 链路继续保留为稳定回滚路径。
```
